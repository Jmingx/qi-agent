# 工具三件套方案：patch 精确编辑 / clarify 澄清提问 / todo 任务清单

日期：2026-08-22 ｜ 状态：待评审 ｜ 来源：Hermes/DSH 工具调研第一梯队（tool-calling.md）

## 背景

对照 Hermes（70+ 工具）与 DSH（能力包制）全量调研后，筛选出第一梯队
纯逻辑工具（无外部依赖、学习价值高）：

| 工具 | 解决的问题 | 参考 |
|---|---|---|
| patch | write_file 整文件覆盖太重——小改动单行替换（省 token + 不覆盖别处） | Hermes patch（V4A + 9 策略模糊匹配）/ DSH str_replace_editor |
| clarify | agent 缺"信息澄清"能力——只有审批弹窗（安全交互），不能问"你要删 A 还是 B？" | Hermes clarify_tool（平台层交互）/ DSH interaction ask-user |
| todo | agent 长任务无法自我追踪——"计划 5 件做完 2 件"靠对话记忆 | Hermes todo_tool（覆盖式写）/ DSH tool-todo |

## 一、patch 精确编辑

### Schema

```
path: string          目标文件（必填）
old_string: string    待替换的原文（必填，精确/容错匹配）
new_string: string    替换后的新文（必填）
replace_all: bool     替换全部匹配（默认 False 只替换第一处）
```

### 匹配策略（Hermes 9 策略的保守子集）

Hermes 用 9 策略链（exact → line_trimmed → whitespace_normalized →
indentation_flexible → escape_normalized → trimmed_boundary →
unicode_normalized → block_anchor → context_aware），非 exact 策略带
escape-drift guard（替换前再校验防误改）。qi-agent 第一版取**前 4 个保守
策略**（宁可报错不误改——容错过度 = 改错位置）：

1. exact：精确匹配
2. line_trimmed：行尾空白容错（\r\n vs \n、行尾空格）
3. whitespace_normalized：空白序列归一（连续空格/制表符）
4. indentation_flexible：整块缩进对齐（模型拷贝时缩进漂移）

找不到 → 返回**可行动错误**（对齐 Hermes format_no_match_hint：报告匹配
次数、文件上下文片段、建议"检查 old_string 是否与文件完全一致"）。

### 原子性与安全

- **原子性**：old_string 匹配失败 → 不写文件（零部分修改）；匹配成功 →
  单次替换（或 replace_all 全部），然后写回
- **安全**（对齐 write_file 四档）：
  - 敏感路径（.env/.git 等）→ 红线拦截（approved 也拒，工具层兜底）
  - 编辑已有文件 = 覆盖写入语义 → **审批档**（security_guard 判档
    NEED_APPROVAL:patch 编辑 <path>——声明式：register(approval=...)）
  - approved 内部参数（模型不可见，防绕过，复用 v0.4.18 机制）
- **diff 展示**：返回 unified diff（difflib）——模型/用户看到改了什么
  （对齐 Hermes/DSH 编辑后展示 diff）

### 边界（描述交叉引用）

```
新建文件 / 整文件重写 → write_file（patch 不建文件）
小改动精确替换（改一行、改一个参数）→ patch
批量多文件操作 / 增删文件 → 远期 V4A 格式（本期不做）
```

### 学习点

difflib unified diff、字符串匹配容错设计（策略链 + 保守哲学：容错是
"位置漂移"风险的来源，guard 校验是必须的）、原子性（先验证后写）。

## 二、clarify 澄清提问（含交互抽象层——用户要求为后续 CLI 形态预留）

### 核心设计：交互与工具分离（对齐 Hermes）

Hermes 明确："实际交互逻辑在平台层（cli.py / gateway），工具层只定义
schema、校验和薄分发器，委托平台回调。"——**这正是为"后续其他形态 CLI"
预留空间的方式**。qi-agent 照抄此架构：

```
┌─────────────────────────────────────────────────────┐
│ 交互抽象层：qi_agent/interaction.py（新模块）          │
│   InteractionProvider（协议/ABC）                     │
│     ask(question: str, choices: list[str] | None,     │
│          timeout: float | None) -> str                │
│   ┌──────────────────────────┐                        │
│   │ TerminalInteraction（CLI）│ ← 本期实现              │
│   │   input() + 选项编号选择  │                        │
│   │   非 tty → fail-safe      │                        │
│   └──────────────────────────┘                        │
│   未来：WebInteraction（HTTP 轮询）/ GuiInteraction /   │
│   消息平台 Interaction —— 换实现，工具零改动             │
└─────────────────────────────────────────────────────┘
          ▲ 注册（模块级 setter，cli.py 启动时注入）
┌─────────────────────────────────────────────────────┐
│ clarify 工具（tools/clarify.py）                      │
│   handler 不直接 input()——调用 provider.ask()         │
│   schema + 参数校验 + 分发（对齐 Hermes 薄分发器）       │
└─────────────────────────────────────────────────────┘
```

- **注册机制**：`set_interaction_provider(provider)`（模块级），CLI 启动
  注入 TerminalInteraction；未注册（评测/库调用）→ clarify 返回
  "[交互不可用]" 错误（fail-safe，不挂死）
- **审批弹窗同构**：approval_gate 的 y/n/a 交互本质也是"ask 带 choices"
  ——接口对齐后未来可统一走 InteractionProvider（本期只对齐接口，不改
  approval_gate，范围控制）

### Schema

```
question: string        问题（必填）
choices: list[str]      选项（≤4，对齐 Hermes MAX_CHOICES；省略 = 开放式）
timeout: float          等待秒数（默认 60；评测场景自动超时 fail-safe）
```

### 与 agent 循环的交互

- clarify 在工具执行阶段（阶段 2）运行，handler 内部**同步阻塞**等用户
  输入（线程池里阻塞，其他并行工具照常执行，主线程按序回填等它）
- 用户回答 → 作为工具结果回填给模型（自然融入对话）
- 评测/无交互环境：provider 未注册或非 tty → 返回错误，模型换策略
  （fail-safe：不挂死评测）

### 边界

```
审批弹窗（y/n/a 安全确认）→ approval_gate（不动）
信息澄清（自由文本/多选）→ clarify
```

### 学习点

交互抽象（协议 + 注册 + 依赖倒置：工具不依赖具体终端）、fail-safe 设计
（无交互环境不挂死）、同步阻塞 vs 事件异步的取舍。

## 三、todo 任务清单

### Schema（单工具 + action 参数）

```
action: string   create | list | update | complete | delete（必填）
title: string    任务内容（create 必填）
id: int          任务 id（update/complete/delete 必填）
status: string   pending | in_progress | completed（update 可选）
```

### 存储与状态机

- **TodoStore**（内存，会话级，每 Agent 一个实例——对齐 Hermes "one
  instance per AIAgent"）
- 状态机：`pending → in_progress → completed`（校验非法状态转换）
- id 自增分配（不重用），列表顺序 = 创建顺序
- 返回：操作后的**全量列表**（模型可见完整状态，对齐 Hermes 写后返回）

### 各 action 行为

| action | 行为 | 非法输入 |
|---|---|---|
| create | 追加任务，返回新 id | title 空 |
| list | 返回全量（含状态） | — |
| update | 改 title/status | id 不存在 |
| complete | 状态置 completed（终态） | id 不存在 |
| delete | 移除任务 | id 不存在 |

### 安全与边界

- 纯内存状态操作，无外部副作用 → **放行**（无审批，approval=None）
- 边界：不做持久化（会话级，对齐 Hermes 内存存储）；未来会话持久化后
  再挂 JSON 存储（工具 schema 不变）
- 学习点：状态机设计（合法转换校验）、CRUD 语义、id 管理

## 决策点（待评审确认）

| # | 决策点 | 意见 |
|---|--------|------|
| 1 | patch 匹配策略：4 个保守策略（非 Hermes 全 9 个） | ✅ 容错=误改风险，保守优先；future 需要再加 |
| 2 | patch 编辑已有文件 → 审批档（对齐 write_file 覆盖判据） | ✅ 声明式 register(approval=...) |
| 3 | clarify 交互抽象层（InteractionProvider + 注册注入） | ✅ 用户明确要求（为后续 CLI 形态预留） |
| 4 | clarify 未注册 provider → fail-safe 错误（不挂死评测） | ✅ 对齐 approval fail-closed 哲学 |
| 5 | todo 单工具 + action 参数（vs Hermes 覆盖式写） | ✅ 显式 CRUD 学习价值高（状态机），token 省 |
| 6 | todo 内存存储（会话级，不持久化） | ✅ 对齐 Hermes；持久化等会话系统 |
| 7 | approval_gate 本期不动（仅接口对齐交互层） | ✅ 范围控制；二期再统一 |
