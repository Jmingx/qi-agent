## 1. 现状

```
/stop → manager.stop(ctx_id) → context.stop() → _stop_flag.set()
agent 循环：每轮开头检查 should_stop() → 下轮生效
→ LLM 调用阻塞中（client.chat() 同步等待）无法中断，要等它返回（最长 60s）

状态机：ChatPhase 已细分（LLM_CALL/TOOL_EXEC/ANSWERING）——"精准中断"的
数据基础已就位，缺的是"如何打断阻塞中的 LLM 调用"
```

## 2. 技术选型（业界对照 + 修正）

### 2.1 业界三个参考实现（2026-08-24 调研）

| | Hermes (Python) | Claude Code (JS) | Pi (TS) |
|---|---|---|---|
| **机制** | 后台线程 + **socket.shutdown 掐断**（F+G） | **AbortController/AbortSignal**（C） | **AbortSignal 全链路传播**（C 工程化） |
| **LLM 调用抽象** | interruptible_api_call（包装函数） | SDK 原生 signal 参数 | **streamFn 依赖注入**（可换实现） |
| **中断传播** | 子 agent + 工具线程 | SDK + 每轮 checkpoint | **所有 hook/工具/子任务全传播** |
| **取消语义** | force_close 后读 `_request_cancelled` 区分 | AbortError 是正常路径 + 区分原因 | `signal?.aborted` 每层检查 |

**关键结论**：
- JS 生态（CC/Pi）：SDK 原生支持 AbortSignal → 方案 C 是标准答案
- Python 同步（Hermes/我们）：openai SDK 不支持取消 → **F+G（线程 + 掐 socket）是 Python 等价答案**
- Pi 的工程化启发：**协作式 checkpoint**（工具执行中不掐断、工具间检查 stop）+ streamFn 依赖注入

### 2.3 方案 F+G + AgentPool 替换（本次采用，用户思路）

```
核心（用户拍板思路）：
  "请求通过异步线程发送（pool 管理），主线程随时可响应 stop；
   不销毁线程——替换 agent 即可（agent 无状态，数据全在 context）"

设计：
  manager.run(ctx_id, input)：
    agent = pool.acquire(ctx)          # 从池取执行者
    后台线程跑 agent.chat(input)        # LLM 请求在后台线程（daemon）
    主线程等 stop_event / done_event    # 双事件等待
    → stop 触发：立即返回"已停止"
                + pool.release(agent)   # 旧 agent 丢弃（线程自然回收）
    → done 先到：正常取结果

  stop 后新请求：
    agent2 = pool.acquire(ctx)          # 新 agent 接管同一 context
    → 无状态替换：行为完全一致（数据全在 context）
    → 旧线程自然结束（timeout 兜底，不阻塞任何东西）
    → "销毁线程" = "丢弃引用 + 换新"（Python 最优解）
```

**为什么对**（对齐 Agent 架构）：
- agent 无状态（数据全在 context）→ 替换零成本
- pool 本来就是 acquire/release 即用即弃 → 完美承接
- 不需要真销毁线程（Python 做不到也不必要）→ "换新"就是最干净的销毁

## 3. Ctrl+C 信号支持（用户评审补充）

### 3.1 现状问题

```
CLI 的 KeyboardInterrupt（Ctrl+C）→ 直接 break 退出（打印"再见"）
→ 用户 Ctrl+C 后程序退出，不能继续对话
→ 交互场景刚需：Ctrl+C 应该"中断当前任务，回到输入提示符"（继续聊）
```

### 3.2 双语义设计（业界标准：按一次中断，按两次退出）

```
第一次 Ctrl+C：触发 manager.stop(ctx_id) → 实时中断当前 LLM 调用
              → 返回"已中断" → 回到输入提示符（继续对话）
第二次 Ctrl+C（1 秒内连续）：退出程序（用户明确要离开）

实现：
  signal.signal(SIGINT, handler) 注册信号处理器
  handler：第一次 → 设 stop 标志（不抛异常——后台 LLM 线程不受影响）
           第二次 → 恢复默认 SIGINT（抛 KeyboardInterrupt → 退出）

  ⚠ 关键：主线程在"双事件等待"（等 stop/done）时收到 Ctrl+C——
    signal handler 设 stop 标志 → 主线程 wait 返回"已停止"
    （不依赖 KeyboardInterrupt 异常冒泡——因为主线程不再阻塞在 client.chat，
     而是阻塞在事件等待，Ctrl+C 由 handler 消费，不抛异常）
```

### 3.3 与 /stop 命令的统一

```
/Ctrl+C 和 /stop 走同一个机制：context.stop()（设 _stop_flag）
  → manager.run 的"双事件等待"感知 → 返回"已中断"
  → 无状态替换：pool.release 旧 agent，新请求新 agent 接管

差异只在触发源：
  /stop：CLI 命令 → manager.stop(ctx_id)
  Ctrl+C：SIGINT handler → manager.stop(ctx_id)（同一调用）
```

## 4. D3 详细方案：掐 socket（真请求级取消，Phase B）

### 4.1 目标

```
Phase A（F+pool）：stop 后主线程返回，但后台 LLM 线程还在跑（等 timeout）
  → 占着 API 连接 + 消耗 token（最长 60s）
Phase B（G 掐 socket）：stop 时直接掐断 HTTP 连接 → AI 立刻停止生成
  → 省 token + 连接立即释放（不等 timeout）
```

### 4.2 可行性验证（2026-08-24 实测）

```
openai SDK 3.0.0 内部结构：
  OpenAI._client                → SyncHttpxClientWrapper
  _client._transport            → HTTPTransport（httpx）
  _transport._pool              → ConnectionPool
  _pool.connections             → 活跃连接列表（list[httpx.Connection]）
  → 连接对象持有底层 socket → 可 shutdown

注意：connections 在无请求时为空（实测 0）——实际连接结构
      Phase B 实施时用真实请求实测（MockTransport 或本地假 server）
```

### 4.3 实现设计（对齐 Hermes force_close_tcp_sockets）

```
def force_close_tcp_sockets(client) -> int:
    \"\"\"掐断所有活跃 HTTP 连接的 socket（不 close FD——Hermes #29507 教训）。\"\"\"
    closed = 0
    pool = client._client._transport._pool
    for conn in list(pool.connections):
        sock = 拿连接底层 socket（httpx 内部：conn._network_stream / _ssl_context 包装）
        if sock:
            sock.shutdown(socket.SHUT_RDWR)   # 发 FIN 打破 pending recv/send
            closed += 1
    return closed

关键安全细节（Hermes 血泪教训 #29507）：
  ⚠ 线程间只 shutdown() 不 close()——FD 安全
    （close() 释放 FD 后可能被内核回收复用 → TLS 记录写进错误文件！
     shutdown() 只是发 FIN，不释放 FD）
  ⚠ 每个请求用独立 client 实例（worker-local）——中断只关当前请求的
    client，不影响其他请求/重试（openai SDK 默认连接池共享，需每个
    LLM 调用 new 一个 client？——Hermes 是 worker 线程各自 new）
  ⚠ 掐断后抛的网络错误（ReadTimeout/RemoteProtocolError）需标记为
    "自己掐的"（_request_cancelled 标志）——防误读为网络 bug 触发重试
```

### 4.4 触发链

```
stop 触发：
  context._stop_flag.set()
  force_close_tcp_sockets(当前 LLM 请求的 client)   ← Phase B 新增
  → 后台线程的 client.chat() 立即抛网络异常
  → agent 捕获 → 判定"已停止"（_request_cancelled）→ 丢弃结果
  → 线程立刻回收（不用等 timeout）
```

### 4.5 边界与风险

```
① client 共享问题：openai SDK 的 OpenAI() 默认连接池——多个并发请求
   共享连接。掐 socket 会误伤同 pool 的其他请求！
   解法：每个后台 LLM 线程 new 独立 OpenAI client（Hermes 同款：
   "Each worker thread gets its own OpenAI client instance"）
   → LLMClient 改造：chat() 内部按线程 new client 或用独立 client 池
② SSL 连接：DeepSeek 是 HTTPS——socket 是 ssl.SSLSocket
   shutdown(SHUT_RDWR) 对 SSL 安全（发 close_notify/直接断）
③ 掐断后错误分类：网络异常需区分"自己掐的"（cancelled）vs 真网络故障
   → _request_cancelled 标志（Hermes PR #6600 教训——级联中断挂起）
④ 幂等：重复 stop 无害（connections 已空则 closed=0）
⑤ 流式模式：chat_stream 的响应迭代会抛异常——同样标记 cancelled
```

### 4.6 验收（Phase B）

```
1. stop 后后台线程在 <1s 内回收（不等 60s timeout）——实测连接断开时间
2. 掐断后错误不触发重试（_request_cancelled 生效）
3. 并发请求互不误伤（独立 client 验证）
4. SSL 连接安全断开（无异常泄漏）
```

## 5. 工业级落地考量（P0-9）

- **可靠性**：daemon 线程 + timeout 兜底（不泄漏）；结果丢弃防污染；
  stop 幂等；agent 替换无感（无状态）
- **安全**：无新权限面；中断不暴露中间状态；线程只 shutdown 不 close
  （FD 安全——Hermes #29507 教训）
- **记忆**：中断时 context 保持（已写消息不回滚，用户可继续）；替换 agent
  数据无缝（同一 context）
- **可观测**：中断事件 `agent/turn-end reason=stopped`（已有）+ 
  `agent/executor-replaced`（新事件——记录 agent 替换）
- **取舍声明**：真请求级取消（Phase B 掐 socket）v1 末做；AsyncOpenAI
  全链路异步 v2（并发场景）；单用户本地场景 F+pool 已满足"用户感知实时"
