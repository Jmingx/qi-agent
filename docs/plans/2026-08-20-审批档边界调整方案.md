# 审批档边界调整方案：硬拒瘦身 + curl/wget 可审批（待评审）

> **状态:** 待用户评审
> **作者:** Hermes（qi-agent 开发会话）
> **日期:** 2026-08-20
> **前置:** v0.4.20（read_file 分页完成）；用户反馈：审批太死 + 硬拒不合理的折衷
> **核心:** 红线（不可逆系统破坏）硬拒 · 其余全部用户可审批

---

## 1. 问题（用户反馈）

1. **审批命令太多太死**：删个文件也弹窗，干啥都束手束脚
2. **硬拒不合理**：rm/del 用户想执行却被"永远拒"
3. 用户明确："删库跑路不允许执行，重启/关机不能执行外，**其他都应该交给用户审批**"

## 2. 边界调整（用户决策）

### 2.1 硬拒（红线，不可执行、不可配置）——瘦身

```
format / mkfs / dd          ← 磁盘级破坏（删库跑路类）
shutdown / reboot           ← 重启/关机（用户：不能执行）
|  >  >>  &&  ;             ← 组合命令语法（保留，理由见 2.3）
```

**移除**：rm/del/rd/rmdir/git push/git reset/curl/wget（都改审批档——用户可审）

### 2.2 审批档（用户可审批）——扩编

```
rm / rmdir / del / rd / git push / git reset --hard / git checkout --
taskkill / net user / reg delete / start
python / py / npm / pip / npx
curl / wget            ← 新增（网络下载可审——用户能看到下载什么）
```

**移除**：shutdown / reboot（改硬拒——不能执行）

### 2.3 为什么组合命令（| 等）保留硬拒

```
前缀匹配盲区：security_guard 审批判定是 command.startswith(前缀)
"echo a | rm -rf /" 以 echo 开头 → 审批档漏检 → 组合里的 rm 抓不到
管道/重定向/分号是攻击常用载体（组合嵌套危险命令）→ 保留硬拒兜底
```

（用户说的"删库跑路"也常以组合形式出现——`dd if=/dev/zero ... | xx`）

### 2.4 敏感路径红线（不变）

.env/.git/密钥文件读写 → 永远硬拒（path_security，不可配置）

### 2.5 红线必须在插件层生效（实现时发现的关键点）

```
漏洞：format/shutdown 原在审批档（_APPROVAL_PREFIXES 有 "format "/"shutdown"）
      → NEED_APPROVAL → 用户同意 → approved=True → 工具层硬拒被跳过 → 可执行！
修复：security_guard 加 _HARDLINE_PREFIXES（format/mkfs/dd/shutdown/reboot）
      ——在审批档判定【之前】直接 [安全拦截]，不产生审批
      （红线不可审批：既不在审批档，插件层也直接拒）
组合语法（| 等）保持工具层兜底：组合命令不产生审批（前缀不命中）→
无 approved → 工具层硬拒生效（不会被绕过）
```

## 3. 涉及文件

| 文件 | 变更 |
|------|------|
| `qi_agent/plugins/security_guard.py` | _APPROVAL_PREFIXES：+curl/wget，−shutdown/reboot |
| `qi_agent/tools/shell.py` | _DANGEROUS_KEYWORDS 瘦身：−rm/del/rd/rmdir/curl/wget/git push/git reset；+shutdown/reboot（从审批档移入）；保留 format/mkfs/dd/组合语法 |

**注意**：shell 硬拒瘦身后，`rm` 等命令在"无审批插件"场景（评测/自动化）会**直接放行执行**？——不！工具层 `approved=False` 时仍拦非白名单命令（`_READONLY_PREFIXES` 检查保留）——rm 不在白名单 → 无 approved 时仍拒 ✅（工具层兜底不变，只是提示语从"危险操作"变成"不在只读白名单"）。
