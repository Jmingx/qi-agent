# 测评打分系统方案（分级打分 + 指标跟踪 + 历史完整保留）

> 日期：2026-08-29
> 状态：待评审
> 关联：10 号 principle（E2E vs 评测本质）、evaluation/ 现状（runner/tasks/report）、
>       18 号 principle（可观测三支柱）
> 用户调整（评审意见）：**历史测评记录必须完整保留**（每 run 全量落盘、永不覆盖）
>       ——趋势分析的前提（只留"上次"看不到曲线）

## 1. 背景与现状

**现状**（evaluation/）：
- 任务定义：expected_tools/forbidden_tools/expected_keywords/expect_blocked/expected_memory（规则断言）
- runner：Semaphore 并发 + 超时保护 + eval/prod parity
- report：通过率 + 分类细分 + 平均轮次/耗时 + last_report.json 回归对比

**缺口**：
- ❌ 任务完成度**分级打分**（只有 pass/fail 二值）
- ❌ token 消耗 / 成本估算（usage 有数据但没进报告）
- ❌ **历史完整保留**（last_report.json 被覆盖——只留"上次"）
- ❌ 历史趋势视图（跨 N 次 run 的指标曲线）

## 2. 指标体系（四类）

```
① 正确性：任务完成度
   二值 passed（规则）+ 分级 score（0-100，judge 质量分）
② 效率
   prompt/completion/缓存命中 token、耗时、轮次
③ 行为（后续扩展）
   工具调用分布、错误重试、审批触发、压缩次数
④ 成本
   token × 单价（DeepSeek 可算——v4-flash 命中 ¥0.02/1M）

每任务记录：{id, category, passed, score, tokens{prompt,completion,cache_hit},
  cost, elapsed, turns, tools_used, failures, history(可选消息级)}
```

## 3. 打分机制（混合：规则保底 + judge 质量分）

```
规则断言（已有）：expected_tools/keywords——硬性要求，不放松
  → 规则不过 = score 0 分 + 短路（不进 judge——省成本）

LLM-as-judge（新增）：任务 + 产物 + 历史 → judge 模型按 rubric 打分
  输出（JSON schema 约束）：{score: 0-100, reason, missing_points[]}
  judge 提示词："只根据提供的证据评分，不脑补"（防 judge 幻觉）

组合：
  passed = 规则全过（守底线）
  score = judge 分数（量质量：完成度/正确性/合理性）
```

## 4. 历史完整保留（用户拍板——核心设计）

```
eval_runs/ 目录（永不覆盖——每 run 全量落盘）：
  eval_runs/
    20260829_103000_report.json   ← 每 run 一个完整 JSON（含每任务明细）
    20260829_103000_history/      ← 可选：消息级历史（调试用，保留最近 N 次）
    runs_index.json               ← 汇总索引（追加式，永不重写）
      [{run_id, run_at, pass_rate, avg_score, total_tokens, total_cost,
        avg_elapsed, avg_turns, task_ids[]}, ...]

原则：
  - 写一次永不覆盖（追加式索引 + 独立 run 文件）
  - 任务级明细全保留（趋势归因的基础）
  - 消息级历史按需保留（磁盘成本：任务多时大——裁剪：仅失败任务保留
    消息历史？或最近 N 次——决策点 D6）
```

## 5. 趋势视图（历史完整保留的价值兑现）

```
趋势报告（跨 N 次 run）：
  通过率曲线 / 完成度均分曲线 / token 总量曲线 / 成本曲线 / 平均耗时曲线
  回归检测：滑动窗口（最近 5 次均值 vs 本次）——趋势比单点可靠
  任务归因：按任务 ID 的跨 run 序列（哪个任务 score 下降/token 暴涨）
  run 对比：任意两次 run 对比（不只 vs 上次）
```

## 6. 决策点

| # | 决策 | 选项 | 建议 |
|---|---|---|---|
| D1 | 打分机制 | A. 规则二值 B. 纯 judge C. **混合** | **C**——规则守底线，judge 量质量 |
| D2 | judge 模型 | A. 复用主模型 B. 独立便宜模型 | **A**——评测低频，成本可接受 |
| D3 | **历史保留** | A. **eval_runs/ 每 run 全量落盘（永不覆盖）** B. 只留上次 | **A**——用户拍板，趋势前提 |
| D4 | 汇总索引 | A. runs_index.json 追加式 B. 每次重建 | **A**——追加式（永不重写历史） |
| D5 | 趋势回归 | A. 只对比上次 B. **滑动窗口** | **B**——趋势比单点可靠 |
| D6 | 消息级历史 | A. 全保留 B. 仅失败任务 C. 不保留（任务级足够） | **B**——调试需要，磁盘可控 |
| D7 | 可视化平台技术栈 | A. **标准库 http.server（零新依赖）** B. Flask（轻量） C. FastAPI | **A**——"简单"优先，符合项目最小依赖哲学（对比 DSH 窄腰） |
| D8 | 平台绑定 | A. **127.0.0.1 本地绑定** B. 0.0.0.0 | **A**——本地可视化，不暴露公网 |

## 7. 工业级落地考量（P0-9）

```
可靠性：
  - 历史永不覆盖（追加式索引 + 独立 run 文件）——数据不丢
  - 写盘原子性：run 文件写完再更新索引（防半写索引）
  - judge 失败降级：judge 调用异常 → score=None（标注"judge 失败"，
    不阻塞评测——fail-continue）
安全：
  - 历史可能含敏感对话（评测任务内容）——本地文件权限（同现有）
  - judge 输入：只传任务/产物/历史（不透传系统提示词/密钥）
记忆：评测历史 = 评测记忆（可对比/可追溯）——与 26 号持续学习呼应
可观测：
  - 趋势报告 = 评测指标可观测（通过率/成本/效率三维演进）
  - runs_index 可查询（按时间/任务过滤）
```

## 8. 验收标准

```
1. 每 run 落盘 eval_runs/<ts>_report.json（含每任务 score/tokens/cost/elapsed）
2. runs_index.json 追加式——历史 run 记录永不消失
3. 规则不过的任务 score=0 短路（不进 judge）——测试
4. judge 打分：rubric 结构化输出（score/reason/missing_points）——schema 校验测试
5. 趋势报告：跨 5 次 run 的指标序列 + 滑动窗口回归告警——测试
6. 任务归因：按任务 ID 跨 run 序列（score/token）——测试
7. 可视化平台：浏览器打开显示测评集/执行控制/结果/趋势——
   并行/串行/单任务三种模式各跑通一次（手工验收）
8. 平台并发防护：run 进行中再次触发 → 拒绝（测试）
9. 全量回归 620+ 绿 + ruff 过（现有评测不破坏）
```

## 9. 可视化平台（本地 Web——简单版）

### 9.1 定位

本地浏览器可视化（`127.0.0.1` 绑定）——展示测评集、控制执行（并行/串行/单任务）、查看结果与历史趋势。**简单**：零新依赖（标准库 http.server + 单页 HTML + Chart.js CDN）。

### 9.2 架构

```
┌─ 前端（单页 HTML + Chart.js CDN）─────────────────────────┐
│ ① 测评集列表（表格：id/分类/名称/最近 score/趋势箭头）      │
│ ② 执行控制（按钮：并行执行全部 / 串行执行全部 / 单任务执行） │
│ ③ 执行进度（x/y 完成——轮询 /api/run/{id}）                │
│ ④ 任务结果展示（score/token/成本/耗时/失败原因 + judge 理由）│
│ ⑤ 历史趋势（折线图：通过率 / token / 成本——Chart.js）      │
└───────────────────────────────────────────────────────────┘
        │ HTTP（JSON API）
┌─ 后端（标准库 http.server + ThreadingHTTPServer）──────────┐
│  GET  /api/tasks          → 测评集列表                     │
│  POST /api/run            → {mode: parallel|serial,        │
│                               task_ids?: []} 启动执行      │
│  GET  /api/run/{run_id}   → 执行状态/结果（前端轮询）       │
│  POST /api/run/single     → {task_id} 单任务执行            │
│  GET  /api/runs           → 历史 run 列表（runs_index）     │
│  GET  /api/runs/{run_id}  → 某次 run 明细                  │
│  GET  /api/trends         → 趋势数据（跨 run 指标序列）      │
└───────────────────────────────────────────────────────────┘
        │ 调 runner + 读 eval_runs/
runner（并行=Semaphore 限流 / 串行=逐个 / 单任务=指定 id）
```

### 9.3 功能映射（用户要求 → 实现）

| 要求 | 实现 |
|---|---|
| 展示测评集 | /api/tasks + 前端表格（含每任务历史表现） |
| 并行执行 | POST /api/run {mode: parallel}——runner Semaphore(3) 限流 |
| 串行执行 | POST /api/run {mode: serial}——逐个执行 |
| 单个任务执行 | POST /api/run/single {task_id} |
| 任务结果展示 | run 结果表（score/passed/tokens/cost/elapsed/failures + judge reason） |
| 历史数据展示 | /api/trends + Chart.js 折线图（通过率/token/成本曲线） |

### 9.4 细节

- **执行并发防护**：平台层防重复触发（同一时刻只允许一个 run——后端 run 状态锁；runner 已有 Semaphore）
- **进度轮询**：前端每 2s 轮询 /api/run/{id}（简单轮询即可，不做 SSE/WebSocket）
- **单任务执行**：runner 需支持按 task_id 过滤（小改——现有 run_all 加参数）
- **安全**：127.0.0.1 本地绑定（D8）——本地数据不出机器；无鉴权（本地可信）
- **零依赖**：标准库 http.server（D7）——不引入 Flask/FastAPI（符合项目最小依赖哲学）

## 10. 落地路径（增量）

```
Phase 1：指标采集扩展（token/成本进 result——resource_monitor 数据管道；
  report 输出 token/成本/score 占位）
Phase 2：打分系统（任务加 expected_rubric；judge 函数；规则不过短路；
  报告显示 score 均分/分布）
Phase 3：历史完整保留 + 趋势（eval_runs/ 目录 + runs_index 追加式 +
  滑动窗口回归 + 任务归因）
Phase 4：可视化平台（http.server 本地 Web：任务列表/并行/串行/单任务/
  结果展示/趋势图——runner 加 task_ids 过滤参数 + 平台层 run 状态锁）
```

**场景账**：四 Phase 增量（不碰现有 620 测试）；judge 成本 = 任务数 × 1 次主模型调用（几十任务 ≈ 几毛钱）；历史磁盘 = 任务级 JSON（几十 KB/run，可忽略）；平台零依赖（标准库）。
