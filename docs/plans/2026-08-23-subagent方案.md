# Subagent 方案（agent-as-tool + 半双工协议 + 受限子集 + 静态授权）

> 日期：2026-08-23
> 状态：待评审
> 关联：`2026-08-18-事件化改造方案.md`（事件总线）、`2026-08-23-ToolExecutor执行闭环方案.md`（工具执行闭环）、`2026-08-23-工具决策码机制方案.md`（ToolDecision）
> 背景：qi-agent 第二梯队能力——subagent（子代理），对齐 Hermes delegate_task / DSH detached agent

## 1. 概念定位（subagent vs multi-agent）

```
subagent（子代理）＝ 一个 agent 临时雇的"外包工"
  ├─ 父发起 → 子独立跑 → 结果结构化回传 → 子消失
  ├─ 层级（父子/临时/结果回传）
  └─ 类比：项目经理外包"调研 X"，只收报告

multi-agent（多代理协作）＝ 多个对等 agent 长期共事（本期不做）
  ├─ 平级/持久/共享通信层（kanban 黑板式）
  └─ v2/v3 方向，本期只做 subagent
```

**解决的问题**：单 agent 上下文墙（一个会话塞不下 20 个文件）、认知墙（一边想改代码一边查文档注意力分裂）、串行墙（调研 A/B/综合只能一步步）、污染墙（子任务中间对话污染父历史）。

## 2. 核心设计：agent-as-tool + 半双工协议

### 2.1 形态

```
delegate_task 工具（agent-as-tool，与 shell 同级）：
  主 agent 自己决定"这个任务该外包"（LLM 驱动拆解）
  编排双入口：工具调用（agent 自动）+ CLI /delegate（用户手动）—— 都走同一实现
```

### 2.2 上下文（父写背景，B 方案）

```
delegate_task(goal=..., context=..., ...)
  goal    ：任务目标（必传，丢给子 agent 的 system prompt）
  context ：父提炼的背景（父在发起调用的那一刻，用自己理解写清楚——
            这就是"协商的廉价版"）
  max_context_tokens：context 超预算 → 复用阶段 C 压缩产物
            （摘要块 + 最近 N 组，零新机制）
```

### 2.3 半双工协议（核心：父单向控 + 子单向回报）

```
为什么不全双工：父 agent 正阻塞在 delegate_task 工具调用里，
  子问父答 → 死锁。业界主流（Hermes steer / DSH direction）都是单向。
  协商落地形态 = partial 回报 + 重新 spawn，不是实时对话。

父 → 子（3 个单向操作）：
  steer  注入补充指令（下轮生效）——纠偏/加信息
  poll   查状态（running/进度）——探活
  stop   强制终止（拿 partial 结果）——止损

子 → 父（2 个单向回报）：
  result  最终结果（正常结束，结构化）
  partial {status: need_more_info, question}——子主动喊"信息不够"，
          父补 context 后重新 spawn（或 resume）
```

### 2.4 生命周期状态机

```
spawn → running → completed（result）
                → failed（error）
                → timeout（超时兜底）
                → stopped（父 stop 强制终止，partial 结果）
```

### 2.5 结构化返回（用户强调，P0）

```
result 必须是结构化 JSON（不是自由文本），约定 schema：
{
  "summary": "子任务完成总结（父 agent 直接可用的结论）",
  "artifacts": ["产出文件路径列表"],
  "status": "completed" | "failed" | "timeout" | "stopped" | "need_more_info",
  "error": "失败原因（status != completed 时）",
  "question": "need_more_info 时向父询问的问题",
  "usage": {"prompt_tokens": N, "completion_tokens": N, "total_tokens": N}
}
子 agent 的 system prompt 里强制要求按此 schema 产出最终回答，
父 agent 拿到后直接解析——不做自由文本猜谜（对齐 DSH structured result）
```

## 3. 受限子集（工具级隔离，双层防绕过）

```
现状事实：agent.py 调 get_tool_schemas()（全局注册表）、executor 用 execute_tool()
  （全局查表）——全是全局单例。方案：白名单参数 + 双层防绕过。

Agent 加 tools 参数：
  agent = Agent(client, tools=["read_file", "search_files", "run_python", "write_file"])

层 1（模型可见）：get_tool_schemas(allowlist) → 只给白名单内工具的 schema
  → LLM 只知道这些工具存在，其他工具【看都看不到】
层 2（执行硬校验）：executor 执行前查白名单 → 白名单外直接拒绝
  → 防绕过：模型即使幻觉出白名单外的工具名，执行层直接拦
  （schema 过滤是软约束，执行校验是硬约束——对齐 approved 内部参数双层设计）

不做独立注册表实例：register() 是全局函数，14 个工具文件都在全局注册，
  独立实例 = 改签名 + 全文件改，收益为零（白名单过滤够了）。
  白名单是"视图过滤"不是"复制注册表"。
```

## 4. 权限请求与授权（用户审批前置，白名单外先问再给）

### 4.1 核心矛盾

子 agent 没有交互层（没人弹窗）——它的审批**不能弹窗**。但"谁给权限"不能只靠主 agent 单方面决定（LLM 可能过度授权）。

### 4.2 机制：主 agent 提议 → 用户审批 → 注入子 agent

```
主 agent 拉起 subagent 前（还在主 agent 流程，交互层可用）：

1. 预测（主 agent 自己分析）：
   根据 goal + context 判断子任务需要哪些【白名单外】权限
   （如"要改 config.py"→ 需要 write 到项目根的权限）
   → 组装权限请求：permission_requests = [
        {tool: "write_file", path: "config.py"},
        {tool: "run_python", mode: "read_write"},
     ]

2. 弹框（此时还在主 agent 流程，用户能看到）：
   agent/tool-approval bail → approval_gate 弹窗
   "subagent 请求权限：写 config.py？(y/n/a)"
   → 用户同意 → 权限进入授权清单；拒绝 → 从子集移除（fail-closed）

3. 注入：
   用户批准的工具/路径 → 注入子 agent 的授权清单（write_paths 白名单扩展）
   → 子 agent 装配时带上完整授权

类比：外包工要进机房 → 先问主管（用户）"这个外包工需要机房权限吗？"
  → 主管点头 → 给门禁卡（注入授权）→ 外包工才能进
```

### 4.3 权限分层

```
层 0（默认子集，无需审批）：只读工具 + run_python 只读模式
  → read_file / search_files / get_time / list_dir / web_search / web_extract
层 1（白名单路径写）：write_paths 内路径的 write_file
  → 主 agent 在 delegate_task 参数里声明即可（默认 safe 区）
层 2（白名单外权限，需用户弹框审批）：
  → 主 agent 预测到任务需要（改项目核心文件/沙箱升级/代码执行）
  → 弹框 → 用户同意才注入
  → 用户拒绝 → 子 agent 该权限缺失 → 任务降级或失败（fail-closed）
层 3（永远不给，硬编码）：
  → shell 代码执行 / rm 等危险工具
  → delegate_task 本身（递归禁止）
  → write_paths 数量上限（≤3 前缀）
```

### 4.4 授权链完整流程

```
主 agent 调 delegate_task(goal, context, tools=默认子集, write_paths=[...])
  → 工具 handler 内部：
    ① 预测：按 goal+context 判断白名单外权限（层 2）
    ② 弹框（主 agent 流程内）：approval_gate 逐个请求用户确认
    ③ 用户批准 → 权限注入子 agent 授权清单；拒绝 → 移除
    ④ 子 agent 装配（Agent(tools=白名单+已批准) + 子审批处理器）
    ⑤ 子调 write_file(白名单外) → 拒绝（fail-closed，审批不可绕过）
    ⑥ 子完成 → 结构化 result 回父
```

### 4.5 审计

授权清单（谁给 subagent 授了什么工具/路径、用户是否批准）记录事件日志——可回溯"子 agent 到底被允许做什么、实际做了什么"。

## 5. 安全底线（硬编码，不可配置）

```
├─ 递归禁止：子集里没有 delegate_task → 子物理上无法再 spawn（结构禁止）
│  └─（防线 2：将来开放 orchestrator 时 max_spawn_depth 封顶）
│  └─（防线 3：spawn 时 token/时间/步数预算，超预算强制终止）
├─ write_paths 必须非空才允许 write_file（空 = 无写权限）
├─ 每任务 write_paths 数量上限（≤3 个前缀）
├─ 危险工具（shell 代码执行/rm 等）永远不在默认子集
├─ 无审批插件时 fail-closed 拒绝（与现有 approval_gate 同语义）
└─ 审计：授权清单（谁给了什么工具/路径）记录事件日志，可回溯
```

## 6. 实现落点（复用现有机制，核心零侵入）

```
qi_agent/tools/builtin/delegate_task.py（新工具，注册进全局注册表）：
  参数：goal / context / tools / write_paths / max_context_tokens /
        timeout / max_steps
  handler 内部：组装子 agent（Agent + 子审批处理器 + 受限子集）→ 跑
  → 结构化 result 返回

qi_agent/agent.py（改动最小）：
  Agent 加 tools 参数（None = 全部，默认不变）
  get_tool_schemas(allowlist) → 过滤

qi_agent/tools/executor.py：
  执行前查白名单（层 2 硬校验）

qi_agent/plugins/builtin/subagent_approval.py（新插件，或并入 delegate_task）：
  子事件总线上的审批处理器（授权清单匹配）

事件总线复用：
  subagent/steer、subagent/poll、subagent/stop（父→子）
  subagent/result、subagent/partial（子→父）
  ——全部走 EventBus，插件/事件点完成，不侵入 agent 核心循环
```

## 7. 决策点

| # | 决策 | 我的建议 |
|---|---|---|
| D1 | 子 agent 用独立 LLMClient 还是嵌套 Agent | **嵌套 Agent**（有工具能力 + 事件循环 + 安全链） |
| D2 | 白名单外权限怎么给 | **主 agent 提议 → 用户弹框审批 → 注入子 agent**（用户审批前置，先问再给） |
| D3 | poll 是否 v1 做 | **v1 做 steer + stop，poll 可选**（探活低频） |
| D4 | 子 agent 默认工具子集 | **只读 + run_python 只读 + write_file(白名单)** |
| D5 | 后台（background）模式 | **v1 同步**（父等子完成），异步留 v2 |
| D6 | batch 并行 | **v1 单任务**，tasks=[...] 并行留 v2 |
| D7 | 子 agent 用主模型还是独立模型 | **复用主模型**（压缩模型配置可覆盖，C3 机制已有） |

## 8. 实施计划（TDD）

```
Phase 1：Agent.tools 白名单（get_tool_schemas 过滤 + executor 硬校验）
Phase 2：delegate_task 工具（嵌套 Agent + 结构化 result + 授权清单）
Phase 3：半双工协议（steer / stop + partial 回报 + 生命周期状态机）
Phase 4：CLI /delegate 手动入口 + 审计日志
Phase 5：评测（subagent 任务：正确委派/授权边界/超时兜底/递归禁止）
```

## 9. 风险

```
- 子 agent 工具调用成本不可控（LLM 多轮）→ 预算兜底（max_steps/timeout）
- 父 agent 过度授权（LLM 可能给太多工具）→ 硬编码上限 + 危险工具排除
- 子 agent 结果不可信（自报）→ 结构化 schema + artifacts 路径可验证
- 子 agent 与父共享全局注册表 → 白名单双层校验兜底
```
