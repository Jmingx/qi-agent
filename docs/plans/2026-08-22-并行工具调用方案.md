# 并行工具调用方案：一次模型响应执行多个工具

> **状态:** ✅ 已评审通过（2026-08-22，决策点：并发 10 用户拍板 20→10、tool-result 位置与监听器线程安全理由修正）
> **作者:** Hermes（qi-agent 开发会话）
> **日期:** 2026-08-22
> **前置:** v0.4.24；用户方向（2026-08-22）：并发控制缓一缓，优先并行工具调用
> **前提实测:** DeepSeek 一次响应返回 2 个 tool_calls（get_time+get_news）✓
> ——模型侧已支持并行返回，agent 侧串行执行是瓶颈

## 背景与收益

现状：agent.py `for call in result.tool_calls:` **串行**执行——模型一次返回
N 个工具调用，逐个执行 + 回填，然后**再调一次 LLM** 拿下一轮。

```
串行（现状）：3 个工具 → 3 次执行 + 1 次 LLM 往返（秒级）    ≈ 1 LLM 往返
并行（目标）：3 个工具 → 3 次执行（并行）+ 1 次 LLM 往返     ≈ 1 LLM 往返
```

**收益**：省的是 **N-1 次 LLM 往返**（每次 2-10s）——数量级提升。
（对比：shell 进程复用省的是 ms 级启动开销，占比 <1%——已放弃）

## 现状（agent.py 112-155 行）

```python
if result.tool_calls:
    self.messages.append(result.assistant_message)
    for call in result.tool_calls:          # ← 串行
        decision = self.events.bail("agent/tool-call", ...)   # 判档
        if NEED_APPROVAL: ... 审批弹窗 ...                    # 用户交互
        output = execute_tool(call.name, call.arguments, internal=...)  # 执行
        self.events.emit("agent/tool-result", ...)
        self.messages.append({"role": "tool", "tool_call_id": call.id, ...})  # 回填
```

## 设计：两阶段（判档/审批主线程串行 → 执行线程池并行 → 回填主线程按序）

```
阶段 1（主线程，同步——快，无阻塞）：
  for call in tool_calls:
    decision = bail("agent/tool-call")      # 纯检查（毫秒级）
    if NEED_APPROVAL: 弹窗（串行——用户交互一次一个）→ 批准注入 approved
    收集 approved 列表：[call1, call2, ...]（全部判档/审批完）

阶段 2（线程池并行——慢的部分）：
  ThreadPoolExecutor(max_workers=4) 并发执行 approve 的 calls
    → {call.id: output} 结果字典（无顺序依赖）

阶段 3（主线程，回填）：
  for call in tool_calls（原顺序）:
    emit("agent/tool-result", ...)          # 事件主线程发（线程安全）
    append({"role": "tool", "tool_call_id": call.id, "content": output})
```

**关键原则**：
1. **判档/审批必须主线程串行**——弹窗是用户交互（一次一个，不能同时弹 3 个窗）；
   判档本身毫秒级，并行无收益
2. **只有 execute_tool 进线程池**——handler 无共享可变状态（每次独立 Popen/
   纯函数），execute_tool 线程安全（已确认：registry 读 + handler 调用）
3. **tool-result 事件与回填回主线程**——EventBus 监听器不保证线程安全，
   并行线程只做"执行"这一件事
4. **回填按 call 原顺序**（模型按 index 对应结果；乱序回填会让模型困惑）

## 决策点

| # | 决策点 | 方案 | 我的意见 |
|---|--------|------|---------|
| 1 | 哪些工具可并行 | **全并行**（模型自行决策调用语义） | ✅ 对齐 Hermes/OpenAI 协议——模型知道工具语义，它选择并行调用就是确认无冲突；max_workers 兜底总量 |
| 2 | 并行上限 | `ThreadPoolExecutor(max_workers=10)`（**用户拍板，20→10**） | ✅ 安全阀非常态——模型实际通常发 2-5 个；最坏 10×run_python ≈500MB 内存（触发条件苛刻）；同时天然是"并发边界"（呼应之前并发控制讨论） |
| 3 | 审批交互 | 主线程串行弹窗（判档先全做完） | ✅ 一次一个弹窗，用户不会同时面对多个 |
| 4 | 事件/回填 | **阶段 3 主线程、按 call 原顺序** emit（含拦截/审批拒绝的 call——与现状语义一致）——理由：**监听器状态非线程安全**（tool_stats `_call_start` 同名覆盖/`count += 1` 非原子、resource_monitor 计数、logger 文件写），不是 EventBus 结构问题（运行时只读遍历安全） | ✅ 2026-08-22 评审修正：理由从"EventBus 不安全"修正为"监听器状态不安全"；并发线程只 execute_tool |
| 5 | 模型侧参数 | 不加 `parallel_tool_calls`（DeepSeek 默认已支持） | ✅ 实测已返回多个；保持现状零改动 |
| 6 | 串行回退 | 单 tool_call 时天然串行（无性能损失） | ✅ 改造对单调用零影响 |

## 风险与边界

- **并行写类工具的顺序不确定性**（两个 write_file 写同一文件）——模型责任
  （它选择并行=确认无冲突）；工具描述可提示"有依赖/写冲突的调用请串行"
- **并行执行的总时长** = 最慢的那个工具（不是和）——超时仍是每个工具独立
  （shell 10s / run_python 10s），并行不改变单工具超时
- **评测**：judge 已支持多 tool_calls（tools_used 集合）——无适配成本；
  并行执行加速评测（多工具任务）
