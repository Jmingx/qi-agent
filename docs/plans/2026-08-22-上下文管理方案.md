# 上下文管理方案（估算 / 裁剪 / 压缩 / 集成）

日期：2026-08-22 ｜ 状态：待评审 ｜ 规模：14 项 TODO（context-management.md）

## 背景

LLM 上下文窗口有限（DeepSeek 约 64K-128K tokens），对话历史只增不减
必然撑爆/费用暴涨/质量下降。qi-agent 当前**无任何上下文管理**（messages
无限累积）。本方案分四阶段落地 14 项 TODO，并配套**测评保障体系**。

## 原理速览（三大手段 + Hermes 生命周期）

```
估算（感知）：知道每轮占多少 token——没有度量就没有管理
裁剪（预防）：超上限丢最旧消息——简单可靠但丢信息
压缩（进阶）：早期历史 → LLM 摘要——保信息但费一次 API 调用

每轮循环（对齐 Hermes ContextEngine 生命周期）：
  发请求 → 收响应 update_from_response(usage) → should_compress 检查
  → 超阈值 compress（早期历史变摘要）→ 下轮用压缩后上下文继续
```

## 测评保障体系（L1-L4，贯穿所有阶段——用户要求）

裁剪/压缩是**手术级操作**（改动发给 LLM 的内容），必须有专项保障：

```
L1 协议正确性（CI 级，每次改动必跑——"不 400"底线，mock API）
   ① tool_calls 消息与其 tool 结果成对（无孤儿）
   ② role 严格交替（无连续同 role）
   ③ 压缩后保留真实 user turn
   ④ system 消息不重复/不丢失
L2 有界性（集成测试，mock LLM 快速跑）
   ① 50 轮对话 token 总量封顶（不随轮数线性增长）
   ② 裁剪/压缩确实触发（消息数下降）
   ③ 内存不爆
L3 事实保持（任务评测，真实 LLM——evaluation 任务集）
   ① 早期关键事实压缩后仍记得（"第 3 轮说的小明"）
   ② sticky notes 用户显式要求的信息裁剪后仍在
   ③ 摘要不丢关键决策/要求
L4 质量回归（对比评测）
   ① 同问题压缩前后答案一致性
   ② 长对话场景答案质量不下降
```

L1/L2 用 mock LLM（快、确定性、进 CI）；L3/L4 走评测任务集（慢、贵）。
**每阶段完成时交付对应层级的保障**（阶段 A 无 L1/L2 需求，阶段 B 交付
L1/L2，阶段 C 交付 L3/L4，阶段 D 补 L3 的 sticky 专项）。

## 阶段 A：上下文感知地基（3 项）

### A1. token 估算器（P0）

```python
# qi_agent/context/estimator.py（新子包 qi_agent/context/）
def estimate_tokens(text: str) -> int:
    """char/4 启发式估算（Hermes _chars_to_tokens 同款，对齐阈值判断用）。"""
    return max(1, len(text) // 4)

def estimate_tool_schemas_tokens(schemas: list[dict]) -> int:
    """工具 schema 的 JSON token 估算（json.dumps 后 char/4）。"""
```

- 中文 char/4 偏高（中文字符信息密度高）——已知局限，注释说明；
  可选升级 tiktoken 精确计数（决策点 D3）

### A2. API usage 跟踪（P1）

- llm.py：`ChatResult` 增加 `usage` 字段（透传响应 usage：
  prompt_tokens/completion_tokens/total_tokens）
- agent.py：累计 `self._usage = {"prompt": 0, "completion": 0, ...}`
- 会话结束（/stats 或退出）打印总消耗（与 tool_stats 联动）

### A3. 上下文构成分解（P1）

- `context/breakdown.py`：`compute_breakdown(messages, schemas) -> dict`
  分段估算：system prompt / 工具 schema / 对话历史 各自 token 占比
- `--debug` 模式每轮展示：`[上下文] 总 X tokens（system 10% / tools 15% /
  历史 75%），占用窗口 45%`

**阶段 A 测评保障**：估算器精度测试（已知文本断言近似值）+ usage 透传
测试（mock 响应带 usage → agent 累计正确）+ breakdown 结构测试。
交付层级：无 L1-L4（纯感知，不改发给 LLM 的内容）。

## 阶段 B：历史裁剪（预防，3 项）

### B1. 滑动窗口裁剪（P0，最难）

```python
# qi_agent/context/window.py
def trim_messages(messages: list[dict], max_messages: int) -> list[dict]:
    """超上限裁剪最旧的非 system 消息（两条死线约束）。"""
```

**两条死线（Hermes 规范 + OpenAI 协议）**：
1. **tool_calls 成对性**：assistant 的 tool_calls 消息与其后所有
   tool 结果消息必须整体保留或整体裁剪——拆散 = API 400
2. **role 交替**：裁剪后不得出现连续同 role——需校验，必要时
   合并（相邻 user 合并为一条）或丢到上一个交替边界

裁剪后注入 anchor（对齐 Hermes）：`[早期对话已裁剪——共 N 条消息]`
（模型知道历史被裁了，不困惑）。

### B2. 工具结果截断统一收口（P0，简单）

- 现各工具各自截断 2000 字符（read_file/shell/run_python 各自为政）
- 升级：registry 层集中截断——`execute_tool` 出口统一处理
  （`_TOOL_OUTPUT_LIMIT = 2000`），工具只管返回，截断策略一处改

### B3. sticky notes（P1，关键信息保留）

- system prompt 维护 sticky 区：`[重要信息]\n- 用户叫小明`
- 用户/agent 可写入（工具 `sticky_set`？或 CLI 命令）——第一版：
  CLI 命令 `/remember <内容>` + agent 通过特定工具写入（决策点 D6）
- **裁剪永不碰 sticky 区**（它是 system 的一部分，窗口裁剪只动历史）

**阶段 B 测评保障（交付 L1/L2）**：
- L1：mock API 校验裁剪后消息序列合法——成对性/交替/无孤儿/400 不发
  （专项测试 `test_window_protocol.py`：构造 50 条混合消息 → 裁剪 →
  断言协议合法）
- L2：mock LLM 跑 50 轮 → token 封顶 + 消息数下降 + 裁剪确实触发
- sticky：裁剪 100 轮后 sticky 内容仍在（L3 的 CI 版，mock 快速版）

```python
                    threshold: float = 0.7) -> bool:
    """总 token 超窗口 70% → 触发（每轮 usage 后检查）。"""
```

### C2. 摘要压缩（P0，核心）

- `compress(messages, client) -> (compressed_messages, summary)`
- 用 LLM **独立对话**调用（不污染主对话上下文）：
  system: "你是上下文压缩器。把对话压缩成摘要，保留：关键事实、
  用户要求、决策、未完成任务、工具结果结论"
- 压缩后历史 = `[system + sticky] + [压缩摘要消息] + 最近未压缩消息`
  （最近窗口保留 N 条不压缩——保细节）
- **压缩后必须保留真实 user turn**（Hermes _ensure_compressed_has_user_turn）
- UI 提示"正在压缩上下文以继续…"

### C3. 压缩模型独立配置（P1）

- config 支持 `compression_model`（默认复用主模型）；接口预留，
  未来可指独立模型/独立 base_url（决策点 D4）

### C4. 手动命令（P2）

- CLI `/context`（看占用构成）+ `/compact`（手动触发压缩）

**阶段 C 测评保障（交付 L3/L4）**：
- L1（压缩版）：压缩后消息序列协议合法（成对/交替/user turn/system）
- L3：评测任务集新增"长对话事实保持"类任务（3 个）：
  - c-long-1：聊 30 轮穿插事实（"我养了只猫叫咪咪"）→ 触发压缩 →
    问"我的猫叫什么"→ 断言答对
  - c-long-2：sticky 信息压缩后仍在
  - c-long-3：压缩后模型不重做已完成工作（todo 联动场景）
- L4：同一问题压缩前/后各答一次 → 关键内容一致性断言（对比评测）

## 阶段 D：集成（3 项，⑫ 记忆会话依赖阶段 3 暂缓）

### D1. todo 状态注入上下文（P1，今天的遗留！）

- `todo.py` 加 `format_for_injection()`（活动任务渲染，只注入
  pending/in_progress——防模型重做已完成工作）
- agent.py：client.chat 前注入**发送副本**（不污染 self.messages）：
  ```python
  send = self.messages
  todo_ctx = format_for_injection()
  if todo_ctx:
      send = self.messages + [{"role": "user", "content": todo_ctx}]
  ```
- 与 sticky 统一收敛为"上下文注入层"（context/inject.py 管理所有注入）

### D2. prompt caching 友好（P2）

- 约束：system + sticky + 早期固定部分放最前（缓存命中区）；变动频繁
  的最近对话放最后；压缩是唯一允许破坏缓存的例外
- 实现检查：裁剪只动尾部（不影响前缀缓存）、压缩摘要替换早期（例外）

### D3. 长对话评测（P2，L3/L4 落地）

- 与 evaluation.md"长对话与上下文管理评测 L1-L4"条目联动执行

**阶段 D 测评保障**：todo 注入集成测试（mock LLM 收到注入消息）+ L3
sticky/todo 专项评测任务。

## 决策点（待评审确认）

| # | 决策点 | 意见 |
|---|--------|------|
| 1 | 触发阈值默认 70% 窗口，可配置 | ✅ 对齐 Hermes |
| 2 | 先裁剪（阶段 B）后压缩（阶段 C） | ✅ 裁剪保底 + 压缩保质量 |
| 3 | 估算用 char/4 启发式（不引入 tiktoken） | ✅ 零依赖；精度足够阈值判断；tiktoken 留可选 |
| 4 | 压缩复用主模型（独立配置留接口） | ✅ DeepSeek 一个 key；配置项预留 |
| 5 | 裁剪后注入 anchor 提示 | ✅ 防模型困惑（对齐 Hermes） |
| 6 | sticky 写入方式：CLI /remember 命令（第一版） | ✅ 简单；agent 写入工具留二期 |
| 7 | 压缩后保留最近 N 条未压缩（N=10 默认） | ✅ 细节不丢；防摘要过度抽象 |
| 8 | 新子包 qi_agent/context/（estimator/window/compressor/breakdown/inject） | ✅ 模块职责单一 |
