## 一、现状与问题

- 现状：`MessageList.tsx` 对每个 `entry.kind === "tool"` 渲染一整行
  （`row tool message-row`：独立 🔧 avatar + 独立 `.tool-card` 气泡）。
  一次"查天气"对话 = clarify→get_time→web_search×2→web_extract×2 等 6+ 个工具 =
  **6+ 个并排大气泡**，视觉噪音大、上下文撕裂。
- 数据流（不可改）：`useMessages` 收 `item/toolCall` 通知逐条 append ToolEntry
  （running），`item/toolResult` 回填 result（✓/⛔ + 摘要 + 耗时）。工具调用之间
  不会插入 assistant 文本；一轮结束以 assistant final 消息（流式 delta）为界。

## 二、参照（Hermes desktop 真实实现，已查证）

Hermes desktop（apps/desktop assistant-ui）：工具调用挂在 assistant 消息下，渲染为
**flat tool stack**——一个 `ToolGroupSlot` 容器内 grid 平铺若干 `data-tool-row`
（每行：状态 glyph(running/error/warning) + 工具名 + 计时/预览），
多工具共用一个视觉块，绝不一个工具一个气泡。测试注释明示：
"Tools render as a flat list ... a pending tool's inline bar is always in the visual flow"。
qi-agent 子任务卡片同风格：单卡片容器 + 内部多行内容。

## 三、设计（渲染层聚合）

### 1. 聚合规则（段）
- 把 entries 中**连续的 tool entry 段**（中间没有 message/subtask entry）聚合渲染为
  一个"工具活动容器"。
- 断段边界：遇到任何非 tool entry（user/assistant/system/subtask）或列表首尾。
  依据：一轮内工具调用天然连续（工具结果回填 → 继续下一步，无文本插入）；
  轮与轮之间必有 assistant 回复/新 user 消息 → 天然断段。
- 局限注释：若极端情况两轮连续工具调用且轮间无任何文本，会合并显示（视觉上仍是
  合理连续工具流）——可接受，代码注释说明。

### 2. 结构
- `MessageList.renderEntry`：tool 分支改为**按段渲染**——预先对可见区 entries 做
  段切分（纯函数 `splitToolRuns(entries)`，返回段列表，每段含连续 tool entry 下标区间）。
- 段渲染 JSX（对齐现有 row 结构）：
  ```
  <div key={段首entry.id} ref={handleRowRef(段首entry.id)} className="row tool-run message-row">
    <div className="avatar tool">🔧</div>
    <div className="bubble-wrap tool-wrap">
      <div className="tool-run">
        {段内每个 ToolCard}
      </div>
    </div>
  </div>
  ```
- 每个工具行继续用现有 `ToolCard` 组件（内部结构 head/参数 details/footer 结果摘要已齐全，
  实时状态更新天然生效）——**ToolCard 组件逻辑不改或只做展示性微调**。
- 单工具段退化为"容器内一行"（视觉 ≈ 现状单卡，但框在容器内——统一规则，无需特判）。

### 3. 样式（style.css）
- `.tool-run`：flex column，gap 8px（行间分隔）；容器卡片外观沿用 `.tool-card` 家族
  （圆角 16、border、panel 背景）。
- 段内行样式：`.tool-run .tool-card` 改为"内嵌行"视觉——去外阴影，保留行内 head/
  details/footer 结构；多行时行间用细分隔（如 1px border-top 或 gap + 无边框）。
- 状态色沿用现有 running(品牌色)/success/blocked 规则，行内 status 徽章不变。
- 若一行是最后一行且段内仅 1 行，视觉与现状一致，无突兀。

### 4. 虚拟滚动适配（MessageList）
- 高度估算：新增 `estimateToolRunHeight(toolEntries)`——段内各行 `estimateToolHeight`
  求和 + 行间距 ×(n-1) + 容器 padding；`estimateEntryHeight` 无法单 entry 表达段——
  改为按段计算：对 entries 先做段切分、每段一个估算值，offsets 按段推进。
  实测高度仍由现有 ResizeObserver 兜底（真实 DOM 高度覆盖估算），所以估算只需大致正确。
- 锚点/滚动：段行 key 与 ref 锚定段首 entry.id；`findFirstVisibleIndex` 等仍按行数组工作
  （行 = 段）。滚动定位（scrollTarget 用于 message 文本）不受影响。
- 最小实现约束：不引第三方库，不重构既有 hooks。

### 5. 不做的事（明确排除）
- 不改通知协议（不给 item/toolCall 加 turn 字段——相邻聚合已够，加协议要动 serve + ws 类型，超范围）
- 不做"段内自动折叠成 N 步"（Hermes 曾用后被自己废弃——flat list 是当前正确形态；
  参数 JSON 的折叠由每行既有 `<details>` 承担）
- 不改 ToolCard 的既有交互（details 展开/收起逻辑复用）
