## 1. 目标

每次开发后跑评测，**自动对比上次基线**并回答："这次改动让 agent 变好了还是变坏了？"

```
开发前（基线）→ 开发后 → 跑评测 → 自动对比 → 输出：
  · 通过率变化（15/16 → 14/16 ▼）
  · 回归任务明细（哪些任务从 ✅ 变 ❌）
  · 改善任务明细（哪些任务从 ❌ 变 ✅）
  · 回归告警（检测到回归 → 提示确认）
```

## 2. 设计原理（导师讲解）

### 2.1 基线机制：last_report.json 即基线（上次 vs 本次）

```
现状：last_report.json 每次评测覆盖（无对比，gitignore）
升级：last_report.json = "上次结果"
     每次评测跑完 → 读上次 → 对比 → 打印 → 覆盖为本次
```

- **不需要多版本存档**（YAGNI）："上次 vs 本次"已覆盖核心场景
  （开发前跑一次存基线 → 开发 → 再跑自动对比）
- 需要历史存档时（如周报），手动复制 last_report.json 即可

### 2.2 状态判定（按任务 id 对比 passed）

| 本次 | 上次 | 状态 | 含义 |
|------|------|------|------|
| ❌ | ✅ | **回归**（regression） | 改动引入了退化（或环境/LLM 非确定性） |
| ✅ | ❌ | **改善**（improved） | 改动修复了问题 |
| ✅/❌ | ✅/❌ | 稳定 | 无变化 |
| 本次新任务 | — | 新增 | 基线没有该任务 |

**通过率变化**：`(本次通过数 - 上次通过数) / 总数`，▲/▼ 符号标注。

### 2.3 非确定性问题的处理（LLM 特性，必须面对）

评测调真实 LLM——**同任务多次跑结果可能不同**（v0.4.14 实测：e1 首跑 ✅ 重跑 ❌，
模型一次用 read_file 一次用 shell）。单次对比可能误报回归。处理：

```
回归时提示："⚠️ 检测到回归——LLM 非确定性可能导致误报，建议重跑一次确认"
```

- **不自动重跑**（成本×2，YAGNI）
- **提示引导**：用户重跑确认，两次都 ❌ 才是真回归
- TODO 记录未来方案：任务跑 2 次取多数（阶段 B）

### 3.3 run.py 集成（跑完自动对比）

```python
def main() -> None:
    results = run_eval()
    # 逐任务打印（现状保留）
    prev = load_report()          # 读上次基线（兼容旧格式）
    if prev:
        cmp = compare(prev, results)
        print(format_compare(prev_run_at, cmp))
    save_report(results)          # 覆盖为本次（即新基线）
```

**流程闭环**：开发前跑（无上次 → 只保存基线）→ 开发 → 跑（有上次 → 对比 + 告警）→ 更新基线。

## 7. 风险与说明

- **LLM 非确定性**：单次对比可能误报回归（e1 案例）——已用提示语缓解；真正的稳定化（跑 2 次取多数）留 TODO（阶段 B，成本×2）
- **基线被覆盖**：每次评测后 last_report.json 更新——"上次"语义清晰；需要历史存档时手动复制
- **任务集变更**：新增任务显示为"新增"（不误判回归）；删除任务不对比（旧 id 缺失时忽略）
- **不做的**：多基线存档管理、CI 自动评测、回归自动重跑验证（均为阶段 B+）
