## 1. 目标

让 qi-agent 在命令行里实现**连续多轮对话**——输入一句话，得到回复，再输入，上下文连贯。这是整个项目的心脏：后续所有功能（工具调用、记忆、技能）都挂在这个循环上。

**本次不做的事（YAGNI）：** 不做工具调用（阶段 2）、不做持久化（阶段 3）、不做配置系统（阶段 4）、不做流式输出（阶段 5b）。

## 2. 技术原理（导师讲解：LLM 对话为什么是"消息列表"）

### 2.1 Chat Completion API 的本质

DeepSeek / OpenAI 的对话接口，本质是一个**无状态函数**：

```
输入：一个消息列表（role + content）
输出：一条新的 assistant 消息
```

```json
// POST https://api.deepseek.com/chat/completions
{
  "model": "deepseek-v4-flash",
  "messages": [
    {"role": "system",    "content": "你是一个有用的助手。"},
    {"role": "user",      "content": "我叫小明"},
    {"role": "assistant", "content": "你好小明！"},
    {"role": "user",      "content": "我叫什么名字？"}   // ← 每次请求都带全部历史
  ]
}
```

**关键认知：模型本身没有记忆。** "多轮对话的上下文" = 客户端把**全部历史消息**每次重新发给 API。模型每次都是"第一次看到这些消息"，只是你发给它的历史让它表现得像记得。

这就是为什么 agent 架构的核心是**消息历史管理**——谁维护消息列表，谁就拥有"记忆"。

### 2.2 role 的三种身份

| role | 含义 | 谁写 |
|------|------|------|
| `system` | 系统指令，设定模型行为/人设 | 开发者（第一条） |
| `user` | 用户输入 | 客户端 |
| `assistant` | 模型回复 | 客户端（收到后原样存回） |

**硬性规则：user 和 assistant 必须交替出现**（不能两条 user 连着），否则 API 报错或行为异常。这要求我们在存历史时严格按"请求-响应"配对追加。

### 2.3 为什么用 openai SDK

DeepSeek 的 API 完全兼容 OpenAI 协议（同样的端点格式、同样的请求/响应结构），所以：
- `openai.OpenAI(base_url="https://api.deepseek.com", api_key=...)` 直接可用
- SDK 自动处理 HTTP、超时、重试、错误解析
- 阶段 2 的工具调用（tool calling）SDK 原生支持，阶段 5 的流式输出也是——现在选对，后面省事

## 3. 架构设计

```
┌──────────┐    输入/输出    ┌──────────┐    消息列表    ┌──────────┐
│  cli.py  │ ──────────────► │ agent.py │ ────────────► │  llm.py  │
│ (REPL)   │ ◄────────────── │ (Agent)  │ ◄──────────── │ (客户端)  │
└──────────┘    打印回复     └──────────┘   回复内容    └──────────┘
                                  │
                                  ▼
                          messages 列表（核心状态）
```

**分层职责：**
- `llm.py`：**只管通信**——发消息列表，拿回复字符串。不知道"对话"是什么
- `agent.py`：**管状态**——维护 messages 列表，实现对话逻辑。不知道网络细节
- `cli.py`：**管交互**——读用户输入、打印回复、处理退出命令。不知道模型是谁

这样分层的好处：将来换模型（llm.py 内部改）、加工具（agent.py 加逻辑）、换界面（cli.py 换实现）互不牵连。

### 4.1 llm.py —— LLM 客户端

```python

        """发送消息列表，返回模型回复文本。"""

```

要点：
- 只暴露一个 `chat(messages) -> str`，内部用 openai SDK 调 `/chat/completions`
- 消息格式就是标准 `[{"role": ..., "content": ...}]`
- API key 从 `.env` 读取（`python-dotenv` 加载，阶段 0 已装）

**为什么 Agent 自己持有 messages 而不是每次从外部传？**
因为"记忆"就是 agent 的身份。把历史封装在 Agent 内部，外部只能通过 `chat()` 交互——这是面向对象封装的核心思想，也方便以后加持久化（阶段 3 只需在 chat 里加一步存盘）。

### 4.3 cli.py —— REPL 入口

```
欢迎使用 qi-agent！输入 exit 或 quit 退出。
你> 你好
agent> 你好！有什么可以帮你的？
你> exit
再见！
```

实现要点：
- `while True` 循环：`input()` 读输入 → 空输入跳过 → `exit/quit` 退出 → 否则 `agent.chat()` 并打印
- 提示符用 `你> ` 和 `agent> ` 区分，直观展示"谁在说话"
- 异常处理：API 调用失败时打印错误并**继续对话**（不崩溃）

### 4.4 配置读取（最小版）

阶段 0 已装 `python-dotenv`。本阶段只在 cli.py 入口处做一件事：

```python
from dotenv import load_dotenv

```

不建配置系统（那是阶段 4），但 API key 必须走 .env——**key 绝不硬编码进代码**。

## 5. 测试设计（TDD）

### 5.1 mock 策略（不真实调用 API）

单元测试**绝不**真实调用 DeepSeek API（会花钱、依赖网络、测试变慢）。做法：mock LLMClient，让 `chat()` 返回固定字符串。

```python
class FakeClient:
    """测试替身：不发真实请求，只记录收到的消息并返回固定回复。"""
    def __init__(self, reply: str = "fake reply"):
        self.reply = reply
        self.received: list[list[dict]] = []   # 记录每次收到的消息列表

    def chat(self, messages: list[dict]) -> str:
        self.received.append(messages)
        return self.reply
```
