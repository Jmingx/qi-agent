# 内核/外壳分离架构方案（Gateway 层 + JSON-RPC 协议）

> 日期：2026-08-28
> 状态：待评审
> 关联：`docs/plans/2026-08-26-主动记忆系统方案.md`（记忆——内核一部分）、
>       `docs/principles/26-2026-08-26-同步架构的生产演进能力评估.md`、
>       并发排查（2026-08-28：stdin 竞争是最大并发风险——本方案根治）

## 一、背景：为什么必须分离（用户拍板：迫在眉睫）

```
现状问题（用户评估 + 并发排查实证）：
  ① CLI（356 行）直接 import 内核组件（build_runtime/remember/interaction/工具）
     ——CLI 耦合了大量命令/stdio 逻辑，无法支撑演进
  ② stdin 竞争（2026-08-28 真实 bug）：审批弹窗（worker 线程 input）
     vs 主线程 input → 同 context 并发 run → 消息污染 400
     → 根因：交互（stdin）与内核（agent 逻辑）在同一进程耦合
  ③ 多外壳不可行：Web/手机/IDE 无法复用 CLI 的 stdio 交互
  ④ 架构撑不住：新命令/新界面/新交互都要改 CLI

业界实证（2026-08-28 调研）：
  Hermes：agent/（内核）+ gateway/（平台层）——clarify_callback 注入
  DSH：core/（内核）+ sdk/（JSON-RPC）+ interaction/（审批独立包）
  Claude Code：queryLoop（内核）+ CLI/SDK/IDE 全收敛到同一循环
  Codex：Agent Core + App Server（JSON-RPC 2.0 over stdio）
  OpenClaw：Agent Runtime + Gateway（WebSocket 控制面）
  → 全部内核/外壳分离，无一让 CLI 直接耦合内核
```

## 二、目标架构

```
┌─────────────────────────────────────────────────────────────┐
│                    外壳（Shell）层                           │
│  CLI 外壳（stdio）│ Web 外壳（WebSocket）│ IDE/其他          │
│  —— 唯一读 stdin/渲染输出的地方                             │
├─────────────────────────────────────────────────────────────┤
│                网关（Gateway）层 ★新                        │
│  JSON-RPC 2.0 协议（自实现 ~100 行）+ 传输（stdio/socket）   │
│  方法集：session/create、message/send、approval/respond、   │
│         stream（通知）、session/stop                         │
│  —— 审批请求-响应（双向）、流式事件（通知）                 │
├─────────────────────────────────────────────────────────────┤
│                    内核（Kernel）层                          │
│  AgentManager（执行权/并发防护）│ AgentContext（数据载体）   │
│  记忆（MemoryStore/提炼）│ 持久化（storage/）│ 工具（tools/）│
│  插件（plugins/）—— 纯逻辑，不碰 stdin/IO 交互               │
└─────────────────────────────────────────────────────────────┘
```

## 三、协议设计（JSON-RPC 2.0 over stdio——自实现）

### 3.1 为什么 JSON-RPC 不用 HTTP（决策记录）

```
HTTP = 单向请求-响应（客户端发起，服务器被动答）
agent 交互 = 双向流式（消息增量/工具调用/审批请求/工具结果）
  审批需要"内核问→外壳答→再回来"——HTTP 状态管理别扭
  流式输出需要长连接——HTTP 每请求建连开销大
JSON-RPC over stdio = 双向长连接（一条管道持续传消息）
  → 审批是会话内往返（request/respond），流式是通知（无响应）
  → 对齐 Codex（App Server JSON-RPC over stdio）/ DSH（sdk JSON-RPC）
HTTP 的定位：外壳↔远端用户（浏览器/公网——那里它擅长），
  内核↔外壳用 JSON-RPC/stdio（本机）
```

### 3.2 自实现 vs 标准库（决策记录）

```
有标准库（jsonrpcserver 等），但业界主流（Codex/DSH）自实现：
  通用库做不了审批双向流/流式事件/类型生成（Codex 亲测 MCP 不够）
JSON-RPC 2.0 协议极简（~10 页规范）：
  请求：{"jsonrpc":"2.0","method":"X","params":{},"id":1}
  响应：{"jsonrpc":"2.0","result":{},"id":1} / {"error":{...}}
  通知：无 id（不需要响应）
→ 自实现 dispatch（~100 行）：解析 JSON → 查方法表 → 调用 → 封装
→ 零依赖 + 完全可控 + 学习价值（对齐 Codex/DSH 做法）
```

### 3.3 方法集定义（对齐 Codex App Server 命名）

```
请求（id 必须有——需要响应）：
  session/create           创建会话 → {session_id}
  session/resume           恢复会话（含持久化加载）
  message/send             用户输入 → 内核处理
  approval/respond         审批响应（approval 请求的回执）
  session/stop             中断当前任务（对齐 /stop）

通知（无 id——不需要响应）：
  item/agentMessage/delta  消息增量（打字机流式）
  turn/diff/updated        工具 diff 更新
  serverRequest/approval   审批请求（内核→外壳弹窗）
  agent/memory-extracted   记忆提炼完成（可观测）

错误码（JSON-RPC 标准）：
  -32700 解析错误 / -32600 无效请求 / -32601 方法不存在
  -32602 无效参数 / -32603 内部错误
  + 自定义：-32001 会话不存在 / -32002 并发运行（RUNNING 拒绝）
```

### 3.4 审批双向流（核心设计）

```
流程：
  1. 内核（agent 工具执行）→ 需要审批
  2. 内核发通知 serverRequest/approval（含命令/参数/上下文）
     → 内核【暂停等待】（类似 wait_stop_or_done 扩展）
  3. 网关转发 → 外壳弹窗（唯一读 stdin）
  4. 用户批准/拒绝 → 外壳发请求 approval/respond（带 approval_id）
  5. 网关回内核 → 内核继续执行（工具执行/拒绝）

实现要点：
  - approval_id：每次审批唯一（关联请求-响应）
  - 暂停机制：内核 wait approval_event（可超时/可取消——abort）
  - 超时策略：默认 60s？超时=拒绝（fail-closed，对齐现有审批）
  - 并发：审批期间内核"暂停"不"崩溃"（根治 400 的根因）
  - 子 agent：无答案者直接失败（对齐 DSH 边界明确）
```

### 3.5 两层交互协议（kernel↔gateway / gateway↔shell）

```
关键设计决策（D8）：
  业界主流（Codex/DSH）= 【一层协议】：
    内核↔网关：进程内（函数/接口调用，无协议）
    网关↔外壳：JSON-RPC over stdio（协议）
  我们 Phase 1 = 进程内解耦 → 内核↔网关也是进程内（Python 方法）
  但为未来【内核独立进程/多网关】预留：
    内核↔网关接口【签名对齐 JSON-RPC 方法】——换传输不换接口

═══════════════════════════════════════════════════
A. 内核 ↔ 网关（进程内接口——Python 方法调用）
═══════════════════════════════════════════════════
  方向：网关调用内核（外壳消息进来 → 网关调内核处理）
       内核回调网关（审批/流式事件 → 内核调网关转发）

  接口（Gateway 方法 → 内核）：
    kernel.create_session(goal) → session_id
    kernel.resume_session(session_id) → status
    kernel.send_message(session_id, text) → 阻塞直到本轮结束
      └ 内部：AgentManager.run（现有——含并发防护）
    kernel.stop_session(session_id) → 中断
    kernel.respond_approval(session_id, approval_id, decision) → 继续执行

  内核 → 网关回调（事件→网关转发外壳）：
    on_approval_request(session_id, approval_id, command, args)
      ← agent 工具执行需审批时触发（内核暂停等待）
    on_stream_delta(session_id, text)       ← 流式输出增量
    on_tool_result(session_id, name, output) ← 工具结果
    on_turn_end(session_id, status)          ← 本轮结束

  实现：内核发事件（现有 events 总线）→ 网关注册监听器转发
  → 复用现有插件事件机制（agent/tool-approval 等）——零侵入

═══════════════════════════════════════════════════
B. 网关 ↔ 外壳（JSON-RPC 2.0 over stdio——协议层）
═══════════════════════════════════════════════════
  传输：newline-delimited JSON（一行一条消息，Codex 同款）
  外壳 = JSON-RPC 客户端，网关 = JSON-RPC 服务端

  外壳 → 网关（请求，带 id）：
    {"jsonrpc":"2.0","id":1,"method":"session/create",
     "params":{"goal":"..."}}
    {"jsonrpc":"2.0","id":2,"method":"message/send",
     "params":{"session_id":"ctx_...","text":"你好"}}
    {"jsonrpc":"2.0","id":3,"method":"approval/respond",
     "params":{"session_id":"ctx_...","approval_id":"ap_1",
               "decision":"approve"}}
    {"jsonrpc":"2.0","id":4,"method":"session/stop",
     "params":{"session_id":"ctx_..."}}

  网关 → 外壳（响应，对应 id）：
    {"jsonrpc":"2.0","id":1,"result":{"session_id":"ctx_..."}}
    {"jsonrpc":"2.0","id":3,"result":{"ok":true}}
    错误：
    {"jsonrpc":"2.0","id":4,"error":{"code":-32002,
     "message":"context 正在运行"}}

  网关 → 外壳（通知，无 id——流式/事件）：
    {"jsonrpc":"2.0","method":"serverRequest/approval",
     "params":{"approval_id":"ap_1","command":"patch 编辑 X",
               "arguments":{...}}}
    {"jsonrpc":"2.0","method":"item/agentMessage/delta",
     "params":{"session_id":"ctx_...","text":"你好"}}
    {"jsonrpc":"2.0","method":"turn/end",
     "params":{"session_id":"ctx_...","status":"completed"}}

═══════════════════════════════════════════════════
C. 完整时序（用户发消息 → 审批 → 输出 → 结束）
═══════════════════════════════════════════════════
外壳              网关                内核
 │  session/create │                  │
 │ ──────────────→ │ create_session    │
 │ ←────────────── │ ────────────────→ │
 │  session_id     │                  │
 │                 │                  │
 │  message/send   │                  │
 │ ──────────────→ │ send_message     │
 │                 │ ────────────────→ │ run(chat)
 │                 │                  │ ─ LLM 调用
 │                 │                  │ ─ 要调工具（需审批）
 │                 │ on_approval ←─── │
 │ approval 通知 ←─ │                  │ 暂停等待
 │ ──────────────→ │                  │
 │ approval/respond│                  │
 │                 │ respond_approval │
 │                 │ ────────────────→ │ 继续执行工具
 │                 │ on_stream ←──── │
 │ delta 通知 ←─── │                  │
 │ ...（流式）      │                  │
 │                 │ on_turn_end ←── │
 │ turn/end 通知 ← │                  │
 │                 │ ←────────────── │ 本轮完成
 │ ←────────────── │ send_message 返回│
 │ 响应 result     │                  │
```

**两层一致性**：内核↔网关接口（A）与网关↔外壳方法（B）【一一对应】
——同一方法（如 approval）在内核是回调，在网关是协议通知，在
外壳是弹窗。改名/加方法 = 三层同步（集中在一个 protocol.py 定义）。

## 四、分层职责

```
内核（qi_agent/kernel/——纯逻辑）：
  AgentManager（register/run/stop/steer——含并发防护）
  AgentContext（数据载体/状态机）
  记忆（MemoryStore/提炼 worker）
  持久化（storage/——SQLite/Markdown）
  工具（tools/——注册/执行/审批事件发出）
  插件（plugins/——事件驱动横切）
  → 不碰 stdin、不碰 UI、不直接 input()

网关（qi_agent/gateway/——新层）：
  JSON-RPC dispatch（协议核心）
  stdio transport（读 stdin 逐行 JSON → dispatch → 写 stdout）
  方法实现（session/message/approval/stream——调内核）
  审批请求-响应桥（内核事件 ↔ 网关请求）
  → 只做协议翻译，不做业务

外壳（CLI 重写为外壳）：
  读用户输入 → 封装 JSON-RPC 请求 → 发网关
  收响应/通知 → 渲染输出（打字机/diff/审批弹窗）
  → 唯一读 stdin/print 的地方

现有文件迁移：
  cli.py（356 行）→ 拆成：
    shell/cli_shell.py（交互/渲染——瘦身 ~150 行）
    gateway/*.py（协议/传输/方法——新）
    kernel/（现有 agents/context/storage 迁入或保持）
```

## 五、分阶段路线

```
Phase 1（进程内解耦——本次）：
  ✅ 建 gateway/（JSON-RPC dispatch + 方法集）
  ✅ 内核接口化：Gateway 方法调 AgentManager（同进程）
  ✅ CLI 重写为外壳（调 Gateway 方法，不再直接碰内核组件）
  ✅ 审批异步化：内核发 approval 事件 → 网关 → CLI 弹窗 → 响应回
     （根治 stdin 竞争——交互只在外壳）
  ✅ InteractionProvider 保留但外壳实现（内核不再调 ask）

Phase 2（跨进程 stdio）：
  ✅ stdio transport（内核进程独立跑，CLI 进程连）
  ✅ 会话由网关拥有（跨 CLI 进程恢复——对齐 Codex thread/resume）

Phase 3（远程 + 多外壳）：
  ✅ socket/WebSocket transport（Web/手机/IDE 接入）
  ✅ HTTP 用户接入层（外壳↔远端用户——HTTP 擅长处）
  ✅ headless defer（对齐 CC——无人值守审批延后）
```

## 六、决策点

```
D1：协议 = JSON-RPC 2.0（自实现 ~100 行）
    对齐 Codex/DSH；HTTP 只做未来用户接入层
D2：传输 = Phase 1 进程内（Python 方法调用）→ Phase 2 stdio
    → Phase 3 socket/WebSocket（可切换，协议不变）
D3：审批 = 请求-响应 + approval_id + 暂停等待 + 超时拒绝
    对齐 Codex serverRequest/approval + DSH ask() await
D4：CLI 瘦身 = 从 356 行拆成外壳（交互/渲染）+ 网关（协议）
    内核组件（agents/context/storage）不迁移（保持现有结构）
D5：内核不碰 IO = 删内核直接 input（interaction 只在外壳）
    根治 stdin 竞争（2026-08-28 真实 bug）
D6：子 agent 审批 = 无答案者直接失败（对齐 DSH 边界明确）
D7：会话归属 = 网关拥有（跨外壳恢复——对齐 Codex thread/resume）
```

## 七、工业级落地考量

```
可靠性：
  - 审批请求-响应带 approval_id + 超时（60s 默认）+ 可取消（abort）
  - 内核暂停等待审批（不崩溃）——根治并发 run 400
  - 网关 dispatch 错误封装（标准错误码）——客户端可区分
  - 会话持久化复用（SQLite——跨外壳恢复）

安全：
  - 审批 fail-closed（超时/无响应 = 拒绝——对齐现有 approval_gate）
  - 审批请求带完整命令/参数（防"Lies-in-the-Loop"——OpenClaw 教训）
  - 凭证不落协议（api_key 内核持有，不经过网关）

记忆：
  - 会话持久化/恢复（SQLite——Phase 2 跨进程恢复）
  - 记忆提炼/注入（内核不变——已实现）

可观测：
  - 网关日志（请求/响应/耗时——JSON 结构化）
  - 流式事件（item/delta、turn/diff）——外壳可渲染 + 可审计
  - 审批审计（approval 请求/响应全记录——对齐 OpenClaw ShieldEvent）
```

## 八、验收标准

```
① CLI 外壳不 import 内核组件（只调 Gateway 方法）
② 审批弹窗不出现 stdin 竞争（交互只在外壳——并发测试通过）
③ 同 context 并发 run 仍被拒（网关层转发 RUNNING 错误）
④ 现有 600 测试全绿（网关/外壳新增测试 + 内核测试不动）
⑤ 手工验收：真实对话 + 审批 + 流式输出正常
```

## 九、遗留（v3+）

```
- WebSocket transport（浏览器外壳）
- HTTP 用户接入层（远程）
- headless defer（无人值守审批延后）
- 类型生成（Codex generate-ts 同款——协议定义生成 TS/Python 客户端）
- 多客户端并发（多外壳同时连同一内核——会话锁）
```
