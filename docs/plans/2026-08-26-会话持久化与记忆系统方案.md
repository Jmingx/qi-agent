> 日期：2026-08-26
> 状态：待评审
> 关联：`docs/principles/26-2026-08-26-同步架构的生产演进能力评估.md`

> 目标：会话持久化（崩溃恢复/会话恢复）+ 记忆系统（跨会话知识）——当前 0% 的最大缺口

## 1. 现状与问题

```
context 数据（messages/turn/usage/status）全在内存——进程退出即失
persist 字段存在但未实现落盘

三个层次（由浅入深）：
  ① 崩溃恢复：进程挂了 → 重启后恢复上次对话（不丢）
  ② 会话恢复：用户离开 → 回来继续聊（/resume <会话>）
  ③ 长期记忆：跨会话的知识积累（"用户喜欢简洁"从对话1带到对话2）
```

## 2. 业界做法（实证）

```
Hermes（Python 生产级）：SQLite 存全量会话 + SessionDB + FTS5 搜索 +
  agent-curated 长期记忆（定期提炼跨会话知识）
DSH（TS 生产级）：session-persistence 包（write-behind 写后置 + coordinator）
  + crash-recovery.e2e 专门测崩溃恢复
Claude Code：~/.claude/projects JSONL 存全量会话 + --resume 恢复

共同模式：
  ✅ SQLite/JSONL 落盘（不是内存）✅ 全量消息存储
  ✅ 会话 ID 寻址（恢复/续聊）✅ 崩溃恢复验证 ✅ 长期记忆独立于会话
```

## 3. 设计

### 3.1 存储层（qi_agent/storage/ 独立包——基础设施）

```
持久化是基础设施（用户拍板独立包）——可复用/可替换/职责清晰：
  qi_agent/storage/          # 独立包
  ├── __init__.py            # 导出统一接口（配置驱动选实现）
  ├── base.py                # 存储抽象基类（接口定义——业务只依赖抽象）
  ├── sqlite_store.py        # SQLite 实现（默认）
  └── jsonl_store.py         # JSONL 实现（可选——v2，若需纯文本）

业务层（context/cli）只依赖抽象接口 → 换存储 = 换实现类
```

### 3.2 SQLite 双模型（快照 + Append 日志——用户拍板两套机制）

```
关键洞察：SQLite 实现"快照"不需要导出 JSON——
  快照 = sessions 表【状态字段】+ snapshot_at 时间点
  日志 = messages 表【逐条追加】（INSERT 天然 append）

表结构：
  sessions(id TEXT PK, title TEXT,
           turn INT, usage TEXT, status TEXT, phase TEXT,
           snapshot_at TIMESTAMP,     -- 快照时间点（恢复时用）
           created_at, updated_at)
  messages(id INTEGER PK, session_id TEXT FK,
           seq INTEGER,               -- 日志序号（重放顺序）
           role TEXT, content TEXT, tool_calls TEXT,
           created_at)
  memory(id INTEGER PK, session_id TEXT, key TEXT, value TEXT,
         kind TEXT, updated_at)       -- 长期记忆

写（append 日志——每条消息追加一行，O(1)）：
  INSERT INTO messages(session_id, seq, role, ...)

打快照（定期/关键点——只更新状态字段，O(1)）：
  UPDATE sessions SET turn=?, usage=?, status=?, snapshot_at=NOW()

恢复（load_session——Event Sourcing 标准：快照 + 增量重放）：
  读 sessions（状态字段 = 快照）
  SELECT messages WHERE seq > 快照时的最大 seq（增量重放）
  → context = 快照状态 + 增量消息

时序示例：
  t0 会话开始 → INSERT session (turn=0, snapshot_at=t0)
  t1 用户"你好" → INSERT message seq=1
  t2 agent"你好！" → INSERT message seq=2
  t3 【打快照】→ UPDATE session SET turn=1, snapshot_at=t3
  t4 用户"帮我写代码" → INSERT message seq=3
  t5 agent 工具 → INSERT message seq=4
  ...崩溃...
  恢复：读 session（快照 turn=1）+ messages seq>2（拿到 3,4）→ 完整恢复

API（base.py 抽象 + sqlite_store.py 实现）：
  append_message(session_id, msg)   # 追加日志（主写入，write-behind 异步）
  snapshot(session_id)              # 打快照（状态字段更新）
  load_session(session_id)          # 快照 + 增量重放
  list_sessions()                   # 会话列表（/resume 用）
  save_memory(key, value)           # 记长期记忆
  load_memories()                   # 取全部记忆（注入上下文）
  delete_session(session_id)        # 删除会话

数据目录：~/.qi-agent/qi.db（对齐 Hermes ~/.hermes，用户私有）
```

### 3.2 会话持久化（崩溃恢复 + /resume）

```
写盘时机（D2——write-behind 异步写，对齐 Hermes/DSH）：
  chat 完成后异步写盘（线程池/后台线程）——不阻塞主流程
  崩溃丢尾（最后一轮未落盘）可接受（Hermes 同款取舍）

崩溃恢复：
  CLI 启动 → 检测上次会话未正常结束 → 提示"检测到未完成的会话，恢复？"
  → load_session → context 恢复 → 继续对话

/resume 命令：
  /resume               -- 列出会话（编号 + 标题 + 时间）
  /resume <id>          -- 恢复指定会话
  /new                  -- 新建会话（当前会话存档）
```

### 3.3 记忆系统（跨会话知识——Markdown 分层，用户拍板修正）

```
业界实证（2026-08-26 调研）：
  Hermes：MEMORY.md（agent 笔记）+ USER.md（用户画像）——Markdown 文件
  DSH：skill 系统（Markdown 技能文件）
  Claude Code：CLAUDE.md（项目记忆）+ 会话 JSONL
  → 长期记忆用 Markdown 文件（可读可编辑 + LLM 友好），不用数据库

为什么 Markdown 不是 SQLite：
  ① 可读性：记忆给人 + LLM 看——Markdown 可读可编辑（SQLite key-value 不能）
  ② LLM 友好：Markdown 是 LLM 训练主流格式（注入效果好）
  ③ 可审计：git 可 diff 记忆变化
  ④ 量小：记忆几十条，文件足够；SQLite 是杀鸡用牛刀

分层（按内容范围）：
  ① 会话内（工作记忆）：context 消息 + sticky（已有）
  ② 长期知识（MEMORY.md）：事实/项目约定/经验（跨会话）
  ③ 用户画像（USER.md）：偏好/身份/关系（用户相关）

文件布局：
  ~/.qi-agent/
  ├── MEMORY.md          # 长期记忆（agent 维护——分节）
  ├── USER.md            # 用户画像（用户维护/agent 提炼）
  └── qi.db              # 会话消息日志（SQLite——恢复/查询）

Markdown 格式：
  # MEMORY.md
  ## 项目
  - qi-agent 是 Python agent 框架
  ## 用户偏好
  - 用户喜欢简洁回答

API（memory_store.py）：
  read_memory() -> str        # 读 MEMORY.md + USER.md（合并注入）
  write_memory(section, text) # 写 MEMORY.md 分节（幂等 upsert 分节）
  list_sections()             # 列出分节（/memory 查看）

注入：pre-step 读 Markdown 记忆 → 注入 system 副本（不污染原消息）
/remember → 写 MEMORY.md 分节 + sticky（会话内）

SQLite 的定位（修正）：
  ✅ 会话消息日志（量大/结构化/要查询）→ SQLite
  ❌ 长期记忆（量小/可读/给 LLM 看）→ Markdown 文件
  → memory 表从 SQLite 移除（不该在数据库）
```

### 3.4 与上下文管理联动

```
压缩后：被压缩的消息存进记忆（关键事实不丢——"压缩后从记忆恢复"）
  → 记忆 = 压缩的安全网（对齐 Hermes：压缩是唯一允许破坏缓存的例外，
    记忆让压缩后的信息可恢复）

长期记忆注入 = 上下文管理的一部分（pre-step 事件挂接）
```

## 5. 决策点

| # | 决策 | 选项 | 倾向 |
|---|---|---|---|
| D1 | 存储介质 | SQLite / JSONL | **SQLite**（Hermes 同款，查询/事务/检索） |
| D2 | 写盘时机 | 每轮同步 / write-behind 异步 | **write-behind**（Hermes/DSH 同款；崩溃丢尾可接受） |
| D3 | 长期记忆来源 | 显式（用户说记住）+ 规则 / agent 自动提炼 | **显式 + 简单规则（v1）**；自动提炼 v2（成本账另算） |
| D4 | 记忆注入方式 | 全量注入 / 相关性检索 | **全量（v1，记忆少）**；相关性检索 v2（embedding） |
| D5 | 恢复入口 | /resume 命令 + 崩溃检测 | **两者**（命令主动恢复 + 崩溃自动提示） |
| D6 | 数据目录 | ~/.qi-agent/qi.db | **~/.qi-agent/**（对齐 Hermes ~/.hermes） |

## 6. 工业级落地考量（P0-9）

- **可靠性**：SQLite 事务（写失败不半写）；write-behind 崩溃丢尾可接受；
  崩溃恢复验证（模拟 kill 测试）；恢复幂等（重复恢复无害）
- **安全**：数据目录权限（~/.qi-agent 用户私有）；记忆不存凭证
  （.env 已有 gitignore）；API key 永不落库
- **记忆**：长期记忆跨会话（本方案核心）；记忆可删（/forget）；记忆去重
- **可观测**：存储事件（session/saved、memory/saved）——审计日志插件可挂；
  数据量可查（/status 显示会话大小）
- **取舍声明**：agent 自动提炼记忆 v2（需 LLM 成本）；相关性检索 v2
  （embedding 依赖）；会话加密不做（本地单用户）；分布式不做

## 7. 验收标准

1. chat 后会话可恢复（进程重启 → load_session 恢复消息/轮数/用量）
2. /resume 列出会话 + 恢复指定会话（继续对话上下文完整）
3. 崩溃恢复：kill 进程 → 重启提示恢复 → 数据不丢（write-behind 丢尾除外）
4. "记住 X" → 长期记忆落库 → 新会话注入 system prompt（跨会话生效）
5. 记忆注入不污染 self.messages（副本注入）
6. 全量测试绿 + ruff 过
