# 上下文压缩策略链方案（策略模式 + 责任链 + 异步化 + 剪枝算法选型）

日期：2026-08-23 ｜ 状态：待评审 ｜ 来源：阶段 C 完成后算法管理演进讨论

## 背景

阶段 C（摘要压缩）已落地（真实 usage 驱动 + 结构化摘要 + L1 协议）。
用户提出三个演进问题：
1. 上下文压缩可以做成**异步**
2. **业界做法**是什么？压缩不会导致原文丢失吗？
3. 是直接丢给模型做摘要，还是**自己控制算法**做压缩？剪枝算法有哪些？

本方案回答这三个问题 + 把"算法管理"重构为优雅的策略链架构。

## 一、问题解答：业界做法与保真策略

### 1.1 业界压缩实现对照

| 方案 | 触发 | 方式 | 保真手段 |
|---|---|---|---|
| **Hermes** | 自动（threshold）+ 手动 /compact | LLM 摘要（独立辅助模型，64K 上下文下限）+ **压缩锁**（TTL + 后台线程刷新防并发） | 结构化摘要分区 + 最近窗口保留 + 压缩后保留 user turn |
| **Claude Code** | 自动 + 手动 /compact | LLM 摘要（同步阻塞） | 摘要 + 最近消息保留 + 锚点提示 |
| **DSH** | compaction 包 | 基础压缩器（LLM 摘要） | 简单摘要替换 |
| **OpenAI 默认** | 自动 | **纯裁剪**（丢最旧，无摘要） | 无（最朴素） |

**结论**：业界主流 = **LLM 生成式摘要**（不是自己写算法）。"自己控制算法"的空间在：
**剪枝（规则化删除）**——摘要的补充/替代。

### 1.2 会不会丢原文？——会，但保真设计分层

所有摘要压缩**必然丢弃原文**（原文被摘要替代）——这是压缩的本质（换 token 空间）。
不丢信息 = 不压缩。业界用 4 层保真设计控制损失：

```
L1 结构化摘要分区：关键事实 / 用户要求 / 决策 / 未完成任务 / 工具结果结论
    ——强制模型按信息类别保留（不是自由发挥的"总结一下"）
L2 最近窗口保留原文：摘要 + 最近 N 组原始消息（细节不丢）
L3 sticky 永不压缩：用户显式要求保留的信息免疫
L4 可追溯锚点：压缩后注入"[早期对话已压缩为摘要]"——模型知道自己
   不知道的，会主动追问而不是假装记得
```

qi-agent 阶段 C 已实现 L1/L2/L4（sticky 挂载 L3 已有）——保真体系完整。

### 1.3 剪枝算法全景（"自己控制算法"的空间）

剪枝（pruning）= **规则化删除**（不用 LLM），按丢弃策略分类：

| 剪枝算法 | 原理 | 保真特性 | qi-agent |
|---|---|---|---|
| **a. FIFO 时间窗** | 最旧先删（滑动窗口） | 保最近，丢最旧 | ✅ 已有（window.py） |
| **b. token 预算** | 删到预算内（逐条数 token） | 预算精确 | ✅ 已有（trim_messages） |
| **c. 消息类型优先级** | tool 结果最可删（中间产物），user/assistant 对话保留 | 保"结论"丢"过程" | 🔜 演进 |
| **d. 内容截断** | 不删消息删内容（长输出留头部） | 保消息骨架 | ✅ 已有（output_limit） |
| **e. 去重/合并** | 连续 user 合并、重复工具结果去重 | 零信息损失（纯冗余） | 🔜 演进 |
| **f. 语义重要性** | LLM/embedding 打分，保留重要消息 | 信息保持最好 | 🔜 演进（贵） |

**剪枝 vs 摘要的分工**：
```
摘要（compress）＝ 语义压缩：保"意思"，丢"字面"（LLM 参与，一次 API）
剪枝（prune）＝ 结构压缩：保"重要"，丢"次要"（规则化，零 API）
组合拳：先剪枝（去冗余/去中间产物）→ 再摘要（语义提炼）→ 窗口兜底
```

## 二、策略链架构（算法管理优雅化）

### 2.1 设计：策略模式 + 责任链 + 注册表

```
context/strategies/            ← 1 策略 1 文件（对齐"1 文件 1 工具"）
  __init__.py                  ← 注册表 + register_strategy 装饰器
  base.py                      ← ContextStrategy ABC
  sticky.py                    ← 挂载策略（幂等，永不消费）
  compress.py                  ← 摘要压缩策略（真实 usage 超阈值）
  prune.py                     ← 剪枝策略（按类型优先级，阶段可选）
  window.py                    ← 裁剪兜底策略（预算）

plugins/context_manager.py = 编排器（零算法逻辑）
  [context_manager]
  chain = ["sticky", "compress", "window"]   ← 顺序可配置（责任链语义）
```

### 2.2 统一接口

```python
class ContextStrategy(ABC):
    name: str  # "sticky" / "compress" / "prune" / "window"

    def should_apply(self, ctx: ContextInfo) -> bool:
        """是否要处理（基于真实 usage 等）"""

    def apply(self, messages, ctx) -> tuple[list[dict], bool]:
        """执行改写；返回 (新消息, 是否消费——责任链处理完就停)"""

class ContextInfo:
    """策略上下文：真实 usage / 配置 / 依赖注入（summarizer 等）"""
    prompt_tokens: int       # post-llm 采集的真实值
    window: int
    threshold: float
    keep_recent: int
    summarizer: Callable
```

### 2.3 对比当前 if/elif

| 维度 | if/elif（当前） | 策略链 |
|---|---|---|
| 新增算法（prune/分段/递归/聚焦） | 插件加 elif 分支 | 新文件 + 注册（零改插件）——开闭原则 |
| 顺序调整 | 改代码 | 改 config chain |
| 职责 | 插件又编排又写逻辑 | 插件纯编排 |
| 测试 | 插件测试裹挟 | 策略单测 + 链集成测试 |

## 三、异步压缩设计（问题 1）

### 3.1 为什么异步

```
同步（Hermes 做法）：触发 → 阻塞 agent 循环 → LLM 摘要（几秒~几十秒）
  → 用户等待（体验差：对话卡住）
异步：触发 → 后台线程跑摘要 → agent 循环继续 → 摘要完成后下轮切换
  → 用户无感知（压缩在后台悄悄完成）
```

### 3.2 快照隔离（并发安全核心）

```
关键：后台线程绝不直接改 agent.messages（并发写 = 竞态）
┌─────────────────────────────────────────────────────┐
│ post-llm 触发（usage 超阈值）                        │
│   → 快照 messages 副本 → 提交压缩任务到后台线程池      │
│   → agent 循环继续（用未压缩历史）                    │
│                                                     │
│ 后台线程：读快照 → 切分（early/recent）→ LLM 摘要      │
│   → 组装压缩结果 → 存"压缩快照"（含生成时消息数）      │
│                                                     │
│ 下轮 pre-step：检查压缩快照就绪？                     │
│   → 快照新鲜（消息数未大增长）→ 原子替换 messages      │
│   → 快照过期（对话已继续很多轮）→ 丢弃快照（防倒退）    │
└─────────────────────────────────────────────────────┘
```

### 3.3 异步的三条防线

```
① 快照隔离：后台只读副本，写完存快照——agent.messages 永远单线程写
② 新鲜度校验：快照生成时的消息数 vs 当前——增长超阈值（如 3 组）丢弃
   （压缩旧快照 = 丢失后续对话，宁可重新压）
③ 单任务锁：同会话同时只允许一个压缩任务（防堆积）；失败静默（下轮重试）
```

### 3.4 异步 vs 同步的取舍（决策点 D1）

| 维度 | 同步（Hermes 同款） | 异步（快照隔离） |
|---|---|---|
| 用户体验 | 卡顿几秒 | 无感知 |
| 实现复杂度 | 低（函数调用） | 中（线程池 + 快照 + 新鲜度） |
| 一致性 | 强（压完即用） | 弱（快照可能过期丢弃） |
| 失败处理 | 当场可知 | 静默重试 |
| 适合 | 手动 /compact（用户主动等） | 自动触发（后台悄悄压） |

**倾向**：自动触发走异步（后台无感），手动 /compact 走同步（用户主动等结果）。
两模式并存 = 策略链里 compress 策略支持 async 开关。

## 四、决策点

| # | 决策点 | 倾向 |
|---|--------|------|
| D1 | 压缩同步 vs 异步 | 自动触发异步 + 手动 /compact 同步（并存） |
| D2 | 策略链顺序 | `["sticky", "compress", "window"]`（可配置） |
| D3 | 剪枝第一版做不做 | **先不做**（当前 window 裁剪已覆盖大部分场景；c/e/f 演进项）——剪枝算法列入策略注册预留 |
| D4 | 异步线程池 | 复用并行工具调用线程池？不——独立单线程 worker（压缩任务低并发，单锁简单） |
| D5 | 快照新鲜度阈值 | 快照后消息组增长 > 3 组 → 丢弃重压 |
| D6 | 压缩模型独立配置 | 复用主模型（阶段 C 现状）；`aux_model` 配置预留（Hermes 辅助模型同款） |
| D7 | /compact 手动命令 | 同步压缩 + 结果展示（CLI 命令，阶段 C 剩余项一起做） |
