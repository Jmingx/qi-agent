## 1. 目标

run_python 增加**内存限制**（v3 三项目标的唯一缺口）：
- 沙箱代码内存暴涨（`x = [0] * 10**9` 瞬间分配 GB 级）→ 子进程被 kill，不拖垮系统
- 输出字节上限（已有 2000 字符截断）和错误隔离（已有子进程）不在本方案范围

**新增依赖**：`psutil`（纯 Python 跨平台进程监控，P1-4 需评审）

## 2. 设计原理（导师讲解）

### 2.1 为什么超时防不住内存炸弹

```
x = [0] * 10**9    # 瞬间分配 ~8GB——不耗时
```

**超时防"时间炸弹"（死循环），防不了"内存炸弹"**（分配瞬间完成）。
Windows 上子进程内存暴涨会吃满系统内存/卡死。

### 2.2 业界方案对照（为什么选 psutil）

| 方案 | 平台 | 说明 |
|------|------|------|
| ulimit -v / RLIMIT_AS | Linux | OS 级，Windows 没有 |
| Job Objects | Windows | P2 TODO（ctypes 复杂） |
| **psutil 轮询** | **跨平台** | 父进程轮询 RSS 超阈值 kill——纯 Python，本项目选择 |

### 2.3 关键设计决策

- **RSS**（常驻物理内存）而非虚拟内存——贴近实际占用（虚拟内存会虚高）
- **轮询间隔 0.5s**：内存炸弹 0.5s 内可能冲到阈值数倍——**阈值留余量**
  （限制 256MB，允许短暂冲到 ~350MB 才 kill，防误杀正常任务）
- **监控进程树**：`children(recursive=True)`——legacy 模式完整 Python 可能再
  spawn 子进程，kill 时整棵树一起杀（Windows 防残留）

## 3. 设计

### 3.1 run_python.py 改造：subprocess.run → Popen 轮询循环

```python
import psutil

# 内存限制配置（可调，默认 256MB——LLM 生成的计算/数据处理足够）
_MEMORY_LIMIT_MB = 256
_POLL_INTERVAL = 0.5  # 轮询间隔（秒）


def _kill_process_tree(proc: subprocess.Popen) -> None:
    """连子进程树一起杀（Windows 防残留）。"""
    try:
        p = psutil.Process(proc.pid)
        children = p.children(recursive=True)
        for child in children:
            child.kill()
        p.kill()
    except psutil.NoSuchProcess:
        pass


def _run_with_limits(cmd, input_data, env, cwd) -> str:
    """Popen + 轮询循环：超时锁（10s）+ 内存锁（256MB）。"""
    proc = subprocess.Popen(
        cmd, input=input_data, env=env, cwd=cwd,
        stdout=subprocess.PIPE, stderr=subprocess.PIPE, text=True,
        encoding="utf-8", errors="replace",
    )
    start = time.monotonic()
    while proc.poll() is None:
        # ① 时间锁：超时 → kill 进程树
        if time.monotonic() - start > _TIMEOUT_SECONDS:
            _kill_process_tree(proc)
            return f"[错误] 代码执行超时（{_TIMEOUT_SECONDS}秒）"
        # ② 内存锁：RSS 超阈值 → kill 进程树
        try:
            mem_mb = psutil.Process(proc.pid).memory_info().rss / 1024 / 1024
        except psutil.NoSuchProcess:
            break  # 进程已退出（正常或异常）
        if mem_mb > _MEMORY_LIMIT_MB:
            _kill_process_tree(proc)
            return (
                f"[安全拦截] 内存超限（>{_MEMORY_LIMIT_MB}MB），"
                f"已终止执行"
            )
        time.sleep(_POLL_INTERVAL)
    # 进程结束：收输出
    stdout, stderr = proc.communicate()
    output = stdout or stderr or "(无输出)"
    if len(output) > _MAX_OUTPUT_CHARS:
        return output[:_MAX_OUTPUT_CHARS] + "\n...[输出已截断]"
    return output
```

**改造点**：
- `subprocess.run` → `Popen` + 手动轮询（run 无法中途监控）
- 超时语义保持（10s kill，返回原提示）
- 新增内存锁（256MB kill，返回 [安全拦截] 内存超限）
- 输出收集：communicate()（进程已结束，无阻塞风险）

### 3.2 与现有防线的关系

```
内存炸弹（x = [0] * 10**9）：
  v1 预检：无 "import os" 等特征 → 放行
  v2 受限环境：x = [0] * N 是合法操作（无文件能力但内存随便用）→ 执行
  v3 内存锁（本方案）：RSS > 256MB → kill ✅ 补上缺口
```

## 8. 风险与说明

- **轮询延迟**：0.5s 间隔下内存炸弹可能短暂冲到阈值数倍（如 1GB）——阈值留余量
  （256MB 限制 + 允许多冲 ~100MB），极端场景（1s 内分配 8GB）可能短暂吃内存——
  完全杜绝需要 Job Objects（P2）或 OS 级限制；psutil 轮询是"够用"的跨平台方案
- **RSS 语义**：Windows 上 RSS 含共享内存（可能高估）——阈值留余量已覆盖
- **Popen 改造风险**：执行路径重构——超时/输出/编码行为必须回归验证（测试覆盖）
- **不做的**：CPU 限制（psutil 也有，但超时已覆盖时间维度，YAGNI）；Windows Job Objects（P2）
