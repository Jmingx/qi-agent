# 2026-08-21 shell 超时死锁修复（打开游戏卡死 agent）

## 问题

用户反馈：让 agent 打开游戏，游戏卡死后 agent 也卡住了。

## 根因（实测复现）

`subprocess.run(command, timeout=10)` 的超时路径在 Windows 上有死锁：

```
cmd.exe /c 游戏.exe   ← shell=True 启动的外壳
  └── 游戏.exe        ← 孙进程，持有 stdout/stderr 管道

10s 超时 → run() 内部 kill 的只是 cmd.exe 外壳
        → 游戏进程仍持有管道 → run() 内部第二次 communicate() 等 EOF
        → 游戏不退出 → 永远等不到 → agent 卡死
```

复现脚本（`subprocess.run('ping -t 127.0.0.1', timeout=3)`）实测：**exit 124
（20 秒被外部超时杀掉）= 永久卡死实锤**。`ping -t` 与"卡死的游戏"行为等价：
不退出 + 持有管道。

## 修复（shell.py）

1. **`subprocess.run` → `Popen` + `communicate(timeout)`**——超时路径自己控制，
   不再依赖 run() 内部的二次 communicate（死锁源头）
2. **超时后 `_kill_process_tree(proc)`**——递归杀进程树（对齐 run_python
   沙箱 v3），清理 cmd 外壳 + 游戏/长驻程序，不留孤儿进程
3. **立即返回**，不再等待管道 EOF（剩余输出丢弃）
4. **可行动提示**：返回信息引导模型"启动长驻程序用 `start` 前缀"
5. **工具描述同步更新**（能力变更必须更新描述——模型要知道 start 的用法，
   否则下轮还会直接运行 exe 再超时）

## 验证

- 复现脚本修复前 exit 124 卡死 → 修复后 **10.0s 精确返回** + 提示
- 新增测试 `test_shell_long_running_timeout_not_hang`（monkeypatch 超时 2s，
  `ping -t` 场景断言快速返回）
- 全量 **245 测试全绿 + ruff 零错误**

## 局限（诚实记录）

- 超时即杀进程树：**正常运行的游戏被直接运行（非 start）时也会在 10s 后被
  终止**——这是"命令超时"语义的必然结果；正确用法是 `start 游戏.exe`
  （异步，立即返回，程序独立运行），工具描述已引导
- 已审批的长驻命令（如用户批准运行的服务器）同样受 10s 超时约束
