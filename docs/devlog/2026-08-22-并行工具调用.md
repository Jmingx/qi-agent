# 2026-08-22 并行工具调用（一次模型响应执行多个工具）

## 需求

用户方向（2026-08-22）：并发控制缓一缓，优先并行工具调用；shell 进程复用
与 run_python 复用经性能账分析后放弃（工具启动开销 ms 级 vs LLM 秒级，
占比 <1%——省的是 1% 的收益，还引入状态串味/隔离破坏）。

## 前提实测

DeepSeek `deepseek-v4-flash` **支持一次响应返回多个 tool_calls**
（实测 2 个：get_time+get_news）——模型侧已就绪，agent 侧串行执行是瓶颈。
（注：模型并行返回不稳定——同 prompt 有时 1 个有时 2 个，机制就绪后
模型支持时自动受益。）

## 实现（agent.py 三阶段改造）

```
阶段 1（主线程串行）：判档（bail tool-call）+ 审批（弹窗一次一个）→ pending 表
阶段 2（线程池并行）：ThreadPoolExecutor(max_workers=10) 只 execute_tool
                      → 拦截的已在阶段 1 定结果，待运行的并行执行
阶段 3（主线程按序）：按 call 原顺序 emit tool-result + 回填 tool 消息
```

- `_execute_with_timing`：并行线程唯一入口（执行 + 计时；不发事件不碰历史）
- `_MAX_PARALLEL_TOOLS = 10`（用户拍板 20→10；安全阀非常态，模型通常发 2-5 个）
- 单 tool_call 天然回退串行（零性能损失）

## 关键设计决策（评审讨论）

1. **tool-result 事件主线程按序 emit**——理由修正：不是"EventBus 不安全"
   （结构运行时只读遍历安全），而是**监听器状态非线程安全**（tool_stats
   `_call_start[name]` 同名并行会互相覆盖、`count += 1` 非原子、logger 文件写）
2. **并行 = 天然的并发边界**：max_workers=10 限制同时执行的工具数 = 最多
   10 个子进程——之前的"全局信号量并发控制"因此缓一缓（先做并行，边界有了）
3. 全并行（模型自行决策调用语义，对齐 Hermes/OpenAI 协议）

## 验证

- 全量 **275 passed + ruff 零错误**（+4：并行执行/事件顺序/拦截也广播/并发证据）
- **并发证据测试**：第一个工具执行等第二个也进入才完成（Event 同步）——
  串行实现必超时失败（RED 确认），并行实现通过（GREEN）
- 手工验收：真实 DeepSeek 一次响应 2 个工具调用 → 两个都执行 + 3.0s 完成
  （串行需 2 次 LLM 往返 ~6s+）

## 遗留

- 模型并行返回不稳定（deepseek-v4-flash 偶发单调用）——模型侧行为，机制已就绪
- 全局并发信号量仍缓一缓（并行 max_workers 已是边界）
- 工具描述可提示"有依赖/写冲突的调用请串行"（模型责任）
