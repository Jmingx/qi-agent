# 工具审批声明式（ToolEntry.approval）——消灭集中表

日期：2026-08-22 ｜ 版本：v0.4.26 ｜ 类型：重构（审批判档声明式化）

## 背景

v0.4.26 上午做了 TOOL_APPROVAL_MAP（工具名 → 审批描述模板集中表），解决
"新增审批工具要改插件硬编码分支"。但表只覆盖**无条件审批**类——write_file
覆盖/越界、run_python 沙箱降级、shell 命令前缀仍是插件里的硬编码分支。

用户提出更彻底的方案：**审批逻辑是工具的固有属性**——ToolEntry 增加
approval 字段，每个工具注册时自声明权限策略，集中表整个消灭。评审通过
（方案 docs/plans/2026-08-22-工具审批声明式方案.md，5 决策点全部确认）。

## 设计

### ToolEntry.approval 三态

```python
@dataclass
class ToolEntry:
    ...
    approval: str | Callable[[dict], str | None] | None = None
    # str      = 无条件审批模板（"删除文件 {path}"，{param} 参数填充）
    # callable = 条件审批函数（返回审批描述或 None 放行）
    # None     = 默认放行
```

register() / @tool 同步支持 approval 参数；registry 新增公开 get_tool(name)。

### 各工具自声明（迁移自 security_guard 硬编码分支）

| 工具 | approval | 迁移来源 |
|---|---|---|
| file_delete | `"删除文件 {path}"`（模板） | TOOL_APPROVAL_MAP |
| write_file | `_approval_condition`（覆盖/越界） | 插件 write_file 分支 |
| run_python | `_approval_condition`（import 白名单外）+ `_RESTRICTED_MODULES` 迁入 | 插件 run_python 分支 |
| shell | `_approval_condition`（CODE_EXEC→沙箱升级；APPROVAL→普通档） | 插件 shell 二档 |
| 其余 6 工具 | None（默认放行） | — |

### security_guard 分层保留

```
保留（系统级底线，硬编码不可关）：黑名单 / 敏感路径 / 红线前缀（HARDLINE）
改为：查 registry → get_tool(name).approval → 模板 format 或调 callable
删除：APPROVAL/CODE_EXEC import、_RESTRICTED_MODULES、_needs_sandbox_downgrade
```

红线不随工具声明的原因（写进注释）：工具注册表可能被动态修改，底线必须
硬编码在插件（安全底线哲学——用户可配置 + 安全底线硬编码双层设计）。

## 为什么比集中表好

1. **单点**：工具的一切（name/schema/handler/approval）一个 dataclass
2. **消灭映射**：name→rule 映射 = 注册表本身，无需额外表
3. **更声明式**：接近 DSH——工具声明"我的权限策略"
4. **契约测试**：register 带 approval 假工具 → 插件自动判档（零改动证明）
