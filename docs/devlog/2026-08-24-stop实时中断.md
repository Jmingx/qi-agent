# devlog: /stop 实时中断（Phase A：F + AgentPool 替换）

日期：2026-08-24
方案：docs/plans/2026-08-24-stop实时中断方案.md（v3 评审通过）

## 做了什么（Phase A：F + AgentPool 替换）

1. **wait_stop_or_done 双事件等待**（context.py）：等待"被停止"或"chat 完成"，
   返回 stopped/done/timeout——manager.run 主线程在这里等（stop 优先检查）
2. **manager.run 实时中断**（agent_manager.py）：整个 chat（LLM + 工具循环）
   放后台线程（daemon）→ 主线程 wait_stop_or_done → stop 触发立即返回
   "已按指令中断当前任务" + pool.release 旧 agent（线程自然回收）
3. **每次 run 清除 stop 标志**：stop 是一次性的，run 重新开始（防残留中断）
4. **协作式 checkpoint**（agent.py 注释更新）：工具批次间检查（工具内不掐断
   由 executor 保证）——Pi 模式，实时中断由 manager.run 主线程负责

## 关键设计（用户思路落地）

```
manager.run(ctx_id, input)：
  agent = pool.acquire(ctx)          # 从池取执行者
  后台线程跑 agent.chat(input)        # LLM + 工具循环（daemon）
  主线程 wait_stop_or_done()          # 双事件等待
  stop → 立即返回"已中断" + release 旧 agent
  新请求 → 新 agent 接管同一 context（无状态替换，数据无缝）

"销毁线程" = "丢弃引用 + 换新"（Python 最优解）
agent 无状态（数据全在 context）→ 替换零成本
```

## 遇到的问题与解决

| 问题 | 解决 |
|---|---|
| stop 后新 run 立即中断（flag 残留） | run 开头 clear stop 标志（stop 一次性） |
| 竞态：stop 太早用户消息未落 | 测试验证：消息在后台线程异步写，stop 后数据保留（context 独立） |
| **stop 后旧线程回填污染（用户指出）** | **竞态防护：LLM 返回后 + 工具回填前查 should_stop——旧线程不回填 assistant/tool 消息**（测试 test_stop_race 实锤：旧线程"回复1"混进 context → 修复后干净） |

## 竞态修复详情（用户评审发现）

```
用户担忧：stop 后旧 agent 线程还在跑，LLM 返回时回填 context → 污染下一轮

实测实锤：context = [system, 第一句, 回复1, 第二句, 回复2]
  ↑ 旧线程的 assistant 消息"回复1"混进来了！

修复（agent.py 两个防护点）：
  ① LLM 返回后、回填前：查 should_stop → 是则返回（不回填 assistant）
  ② 工具执行后、回填前：查 should_stop → 是则返回（不回填 tool）

剩余窗口（诚实评估）：
  - 微秒级"检查后-append 前"——概率极低
  - 用户消息（用户真说的话）保留——语义可接受
  - 彻底防御 = generation 代次机制（v2 TODO——多并发写 context 时再上）
```
