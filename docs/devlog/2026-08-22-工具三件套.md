## 一、patch 精确编辑

### 设计演进（关键踩坑）

**初版整行对齐匹配 → 重写为正则策略链**：
- 初版按"行块对齐"实现（splitlines 逐行比较）——但 old_string 是**文本
  片段**（"a=" 这种行内子串），整行匹配对子串失败
- 重写：把 old_string 转正则，**在原文上搜索**——匹配区间天然准确，
  无归一化偏移映射问题（映射是 fuzzy 匹配最容易出错的点）

### 最终策略链（Hermes 9 策略的保守子集 3 个）

| 策略 | 正则 | 覆盖 |
|---|---|---|
| exact | `re.escape(old)` | 精确 |
| whitespace_flexible | 空白序列 → `\s+` | 行尾/空白/换行容错合一 |
| indentation_flexible | 行首 `[ \t]*`，行间 `\s*` | 缩进漂移 |

### 关键实现点

- **lambda 替换**：`pattern.sub(lambda m: new_string, ...)`——new_string 含
  反斜杠（Windows 路径）时 sub 的替换串会解释 `\1` 组引用，lambda 返回
  字面值杜绝转义 bug
- **原子性**：匹配失败不写文件；成功才落盘
- **安全**：敏感路径红线（approved 也拒）+ 编辑已有文件 = 覆盖语义 →
  无条件审批（声明式 approval="patch 编辑 {path}"）
- **diff 展示**：difflib unified_diff（截断 2000 字符）

### 踩坑记录

1. 整行对齐匹配对行内子串失效（"a=" 不匹配 "a=1\n"）→ 正则策略链重写
2. `_split_new_lines` 最后一行漏换行符 → 替换后丢末尾 \n（内容行都带
   换行，new_lines 必须每行都带）
3. `start or next` 链接策略会吞掉下标 0 的匹配（0 是 falsy）→ 显式循环

## 二、clarify 澄清提问（交互抽象层）

### 架构：工具与交互分离（用户要求为后续 CLI 形态预留）

```
qi_agent/interaction.py —— InteractionProvider 协议
  ├─ TerminalInteraction（本期：input + 选项编号，非 tty fail-safe）
  ├─ 未来 Web/GUI/消息平台：实现协议 + 注册，工具零改动
  clarify 工具 = 薄分发器：schema + ask_user() 委托（对齐 Hermes）
```

- 注册机制：`set_interaction_provider()`（CLI 启动注入）
- fail-safe：未注册/非 tty → InteractionUnavailableError → 工具返回
  [交互不可用]（不挂死，对齐 approval fail-closed 哲学）
- timeout 参数接受但不强制（Windows 无 signal.alarm；评测走非 tty 路径）
- 选项 ≤4（对齐 Hermes MAX_CHOICES）+ 自动"其他"分支

### 踩坑记录

- 测试污染：test_clarify 注册 provider 不清理 → 泄漏到后续 fail-safe
  测试（ask_user 拿到上一个 FakeProvider）→ 每文件 autouse fixture 清理

## 三、todo 任务清单

### 设计

- 单工具 + action 参数（create/list/update/complete/delete）——显式
  CRUD 学习价值高、token 省（对比 Hermes 覆盖式写全列表）
- TodoStore 内存会话级（进程级单例 + _reset_store 测试隔离）
- 状态机：pending → in_progress → completed（**completed 终态不可回退**
  ——防模型把已完成改回 pending 制造"假进度"）
- id 自增不重用；返回操作后全量列表（模型可见完整状态）
- 纯内存无副作用 → 放行不审批（approval=None）
