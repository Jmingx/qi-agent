## 核心架构

```
storage/（独立包——基础设施）
  base.py          存储抽象接口（业务只依赖抽象）
  sqlite_store.py  SQLite 实现（stdlib 零依赖，单文件）
  __init__.py      get_storage() 单例（配置驱动选实现）

接入点：
  manager.run 完成后 → write-behind 异步落盘（后台线程）
  memory 插件 → pre-step 瀑布注入长期记忆（不污染原消息）
```

## 双模型：快照 + Append 日志（Event Sourcing）

```
关键洞察：SQLite 实现"快照"不需要导出 JSON——
  快照 = sessions 表【状态字段】+ snapshot_at 时间点（O(1) UPDATE）
  日志 = messages 表【逐条追加】（INSERT 天然 append）

写：append_message（每条消息一行，O(1)）
快照：snapshot()（更新 turn/usage/status/phase 字段，O(1)）
恢复：load_session() = 读快照状态 + 重放快照后增量消息

类比（Java）：
  Event Sourcing = 银行流水（所有操作记录下来）
  Snapshot = 对账单（某个时间点的汇总）
  恢复 = 最近对账单 + 流水重放（不用从头算）

对比 JSONL：
  SQLite 赢在事务（写一半崩溃→回滚不半写）+ 查询（SQL 检索）
  JSONL 赢在简单（直接读）；但 agent 场景 SQLite 完全够轻
```

## 为什么 write-behind（异步写盘）

```
每轮同步写盘：对话慢（磁盘 I/O 阻塞 LLM 调用）
write-behind（异步）：对话不阻塞，后台线程落盘
  → 崩溃丢尾（最后一轮未落盘）可接受（Hermes/DSH 同款取舍）
  → 恢复 = 最近快照 + 已落盘日志（丢的只是没写完的最后一轮）

类比：银行 ATM 取款记录（先响应后记账——记录可能延迟但不会丢已记账的）
```

## 记忆系统设计（Markdown 分层——用户评审修正）

```
分层（按内容范围）：
  ① 会话内（工作记忆）：context 消息 + sticky——已有
  ② 长期知识（MEMORY.md）：事实/项目约定/经验——agent 维护
  ③ 用户画像（USER.md）：偏好/身份/关系——用户相关

为什么 Markdown 不是 SQLite（业界实证）：
  Hermes：MEMORY.md + USER.md（Markdown 文件）
  DSH：skill 系统（Markdown 技能）
  CC：CLAUDE.md（项目记忆）
  → 长期记忆用文件（可读可编辑 + LLM 友好 + git 可审计）
  → SQLite 只存会话消息（量大/结构化/要查询）

注入机制（pre-step 瀑布）：
  LLM 调用前 → memory 插件读 MEMORY.md + USER.md → 注入 system 副本
  → 不污染 self.messages（副本操作）
  → 前缀稳定区（prompt caching 友好）

来源（v1）：
  显式 /remember（sticky + MEMORY.md 双落点）
  /memory 查看
  v2：agent 自动提炼（LLM 成本账另算）
```

## 与上下文管理的联动

```
压缩后：关键事实可存进记忆（"压缩后从记忆恢复"）
  → 记忆 = 压缩的安全网（压缩丢的信息可从记忆找回）
  → 这是上下文管理"不够深入"的补全（用户直觉：压缩只丢不存）

todo 注入（已有）+ 记忆注入（新增）= 统一"上下文注入层"
  （pre-step 瀑布多个监听者：裁剪 → 记忆 → todo → LLM）
```
