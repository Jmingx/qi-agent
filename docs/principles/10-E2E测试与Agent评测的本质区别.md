# 10 E2E 测试 vs Agent 评测：本质区别辨析

> 归档：2026-08-20 · 来源：回归基线对比方案评审问答（"测评跟 E2E 验证有啥区别"）
> 读者：agent 开发小白（有 Java 背景）
> 关联：docs/principles/02（Agent 循环）、docs/plans/2026-08-20-测评系统阶段A方案.md（业界对照 1.5 节）
> 核心：形式上同构（用例→执行→断言），本质不同——**E2E 测确定性代码的 bug，评测测非确定性组合体的能力**

---

## 1. 用户最初的直觉（部分正确）

> "测评跟 E2E 的验证没啥区别，也是通过用例来测试 agent 的能力，只不过更像 E2E 的验证？"

**对的部分**：结构确实同构——都是"预定义用例 → 执行被测系统 → 断言结果"：

| E2E 测试 | Agent 评测 |
|---------|-----------|
| 预定义用例 | EvalTask 任务集 |
| 执行被测系统 | agent.chat() 跑真实 LLM |
| 断言结果 | judge 规则判定 |

**但"像"到这里为止**——本质区别在"被测对象"和"断言性质"。

## 2. 本质区别（三个维度）

### ① 被测对象：确定性代码 vs 非确定性组合体

```
E2E：被测的是【代码】——执行路径由程序逻辑决定，结果可精确预测
评测：被测的是【代码 + LLM + 工具 + 插件】的组合体——关键决策者是 LLM，
      模型"选哪个工具、怎么从错误恢复、被拦后怎么反应"都不可预测
```

**类比**：
- E2E = 出厂检测（零件按规格检查，结果确定：气缸压力必须 12.5±0.1）
- 评测 = 道路测试（真实路况 + 驾驶员（LLM）行为多变：同一段路每次成绩不同）

### ② 断言：精确匹配 vs 宽松规则

```
E2E：断言精确——输出 == 期望值，失败 = 100% 是代码 bug
评测：断言宽松——关键词 OR（模型用词多样："拦截"/"拒绝"/"禁止"）、工具名、
      拦截标记；失败【不一定是代码 bug】
```

### ③ 可重复性与失败含义（最关键）

| 维度 | E2E 测试 | Agent 评测 |
|------|---------|-----------|
| 可重复性 | **100%**（同输入同输出） | **不保证**（LLM 非确定性） |
| 失败含义 | 代码 bug（可信，直接修） | 能力不足 **或** LLM 波动（**需重跑确认**） |
| 目的 | 防**代码**退化 | 防**能力**退化 |
| 断言者 | 断言代码 | **LLM 本身被测试** |

**一句话**：E2E 测"代码有没有写对"（bug 检测，确定性），评测测"agent 组合体能不能
干活"（能力评估，概率性）——评测是 E2E 的"概率化、能力导向"变体，这是 agent 工程
区别于传统软件工程的核心特征。

## 3. 两种"E2E"要分清（Hermes 分层对照）

| | Mock LLM 集成测试 | 真实评测 |
|---|------------------|---------|
| 别称 | "确定性 E2E" | "能力评估" |
| LLM | 假（mock） | 真 |
| 断言 | 确定（可重复） | 宽松（概率性） |
| 测什么 | **代码逻辑**（agent 循环/工具链对不对） | **模型+代码组合的表现**（能不能完成任务） |
| 项目对应 | test_agent.py 的 FakeClient / test_agent_events.py | evaluation/（阶段 A 任务集） |

**互补关系**：
- mock E2E 保证"代码没写错"（确定性、零成本、进 CI）
- 真实评测保证"agent 能干活"（概率性、花 token、手动跑）
- **两者都不该缺**——缺失任何一层，agent 质量都有盲区

## 4. 为什么评测的"用例"长得像 E2E 用例

因为**任务本身就是行为契约**——评测任务（EvalTask）定义了"输入 + 期望行为"
（期望工具/期望结果/期望拦截），形式上与 E2E 用例同构。区别在：
- E2E 的期望是**精确值**（代码必须产出）
- 评测的期望是**行为模式**（LLM 可能用多种路径达成）

这是"面向行为的测试"与"面向结果的测试"之分——agent 评测被迫面向行为
（因为结果不可预测），这也是 judge 用 OR 关键词/工具名断言的深层原因。
