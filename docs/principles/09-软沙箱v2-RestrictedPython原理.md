# 09 软沙箱 v2：RestrictedPython 原理（principles/05 的升级篇）

> 归档：2026-08-20 · 来源：沙箱主线原理讲解问答（"AST 重写怎么防住"）
> 读者：agent 开发小白（有 Java 背景）
> 关联：principles/05（run_python 沙箱三方案原理——v1 的完整设计）、docs/todos/tool-calling.md（软沙箱升级 v2，P1）
> 定位：v1（黑名单）→ v2（RestrictedPython）升级的技术原理——从"拦什么"到"给什么"

---

## 1. v1 的本质缺陷（为什么要升级）

v1 是**静态特征扫描**（黑名单）：

```python
_FORBIDDEN_PATTERNS = ("import os", "eval(", "().__class__", ...)
if pattern in code:
    return "[安全拦截] ..."
```

**局限（v1 docstring 的"诚实局限"）**：

```python
"impo" + "rt os"            # 拼接：特征不存在于源码
import pathlib              # 白名单外模块：Path('x').read_text() 照样读文件
getattr(__builtins__, "op" + "en")   # 反射拼出 open
```

**本质**：黑名单 = "我知道的攻击都拦"，**不知道的攻击不拦**。特征匹配是猫鼠游戏。

## 2. 核心认知转变：不是"拦什么"，而是"给什么"

```
v1 黑名单：   默认全放行 → 拦掉已知危险   → 未知危险漏网
v2 受限环境： 默认全拒绝 → 只给安全的东西 → 未知危险也没东西可用
```

类比：v1 是"查行李的安检"（按违禁品清单）；v2 是"只给你一个装好物品的房间"——
**房间外的任何东西物理上碰不到，根本不需要知道"违禁品长什么样"**。

## 3. 两大机制

### 机制 ①：AST 重写（编译期）——制造"必经之路"

RestrictedPython 用 `ast` 解析代码 → 遍历语法树 → **重写每一个危险操作点**：

```python
# 你写的代码                    # 编译后（伪码）
x = obj.attr              →    x = _getattr(obj, 'attr')   # 属性访问 → 受限函数
import os                 →    _import_('os')              # import → 受限函数
y = lst[0]                →    y = _getitem(lst, 0)        # 下标 → 受限函数
```

**关键认知：改写本身不防，改写 + 受限函数 = 防。**

- **不改写**：`obj.__class__` 是虚拟机层面操作，直接查对象字典——**没有中间人**，没有地方写"拒绝"
- **改写后**：所有访问强制经过 `_getattr` 函数——函数是我们提供的，里面写着检查逻辑
- 改写的意义 = **"让所有车不得不经过保安亭"**，防护逻辑在保安亭（受限函数）里

> Java 类比：`obj.field` 编译为 `getfield` 指令（虚拟机层面）；ASM 插桩替换为
> `GuardedAccess.getField(obj, "field")` 调用——插桩本身不防，守卫方法体里的检查才防。

### 机制 ②：受限运行时环境（执行期）——房间里的"家具"是挑过的

```python
safe_globals = {
    "__builtins__": safe_builtins,   # 受限内建：print/len/range... 无 open/eval/exec/__import__
    "_getattr": guarded_getattr,     # 属性守卫：双下划线属性受限
    "_import_": guarded_import,      # import 守卫：白名单模块（默认空）
    "_getitem": guarded_getitem,
    ...
}
exec(bytecode, safe_globals)        # 受限房间执行
```

**双保险**：编译期代码被改写（绕不过），运行期守卫再查一遍（改写的代码也必须过守卫）。

## 4. 逃逸链为什么被防住

经典逃逸：`().__class__.__bases__[0].__subclasses__()` → 找 open

```
v1：源码有 "().__class__" 特征 → 拦（但 "()" + ".__class__" 拼接就过了）
v2：().__class__ → _getattr((), '__class__') → 守卫：双下划线属性不在安全名单 → AttributeError
    （第一步就走不动，链子根本不存在——不需要认识逃逸链）
```

## 5. 扫"字符串" vs 重写"语法树"（拼接为什么骗不过 v2）

| | v1 | v2 |
|---|----|----|
| 看什么 | **源码字符串**（文本） | **语法树**（代码结构） |
| `"impo"+"rt os"` | 文本扫描无特征 → 放行 → 运行时拼出真 import | 语法树里是【字符串相加】节点（安全，不改写）；import 语句是【Import 节点】→ 必被改写 |
| 为什么 | 拼接发生在运行时，扫描发生在编译前 | **重写发生在编译期**——看的是结构不是文字，模块名/属性名怎么拼都一样被改写 |
| 终极原因 | — | **运行时拼不出语法**：import 是语句不是表达式，字符串相加结果只是字符串，要执行只能走 eval/exec/__import__——而这些也全部受限 |

**一句话**：v1 在"文字"层面拦（文字可拼接），v2 在"结构"层面拦（**结构拼不出来**）。

## 6. 对比总表

| 维度 | v1 黑名单 | v2 RestrictedPython |
|------|----------|---------------------|
| 默认策略 | 全放行，拦已知 | **全拒绝，给安全集** |
| 拦截层 | 源码特征扫描 | AST 重写 + 受限运行时 |
| 拼接/反射绕过 | ❌ 可绕过 | ✅ 无效 |
| 未知攻击面 | 靠特征追赶 | 受限环境外无路可走 |
| 依赖 | 无 | RestrictedPython（纯 Python，Zope 社区几十年维护） |
| 代价 | — | 双下划线属性受限（少数正常代码跑不了）；属性访问有守卫开销 |

## 7. 诚实局限（v2 也不是万能）

1. **双下划线属性全面受限**——依赖 `__class__`/元类的库代码可能跑不了（LLM 生成的计算/数据代码通常用不到）
2. **性能**——每次属性访问过守卫，微秒级开销（短代码可忽略）
3. **守卫配置要谨慎**——RestrictedPython 历史上也出过逃逸（如配了 `__import__` 放行就废了）——**保持默认严格配置**
4. **不是 OS 级隔离**——防"代码层面的危险"，防不了"子进程被攻击"——所以保留子进程执行 = 双保险（受限解释器 + 进程隔离）

## 8. 与 v1 的共存策略（方案决策点预告）

- **A. 替代**：v1 静态扫描全撤，交给 v2（干净，但失去"快速失败"——明显恶意代码不用等编译）
- **B. 双层**：v1 静态扫描保留为"快速预检"（先拦明显恶意，省子进程）+ v2 主防线（兜底一切）
