# 08 工具调用的短路拦截设计（bail 决策 + 回填协议）

> 归档：2026-08-18 · 来源：事件化改造（v0.4.8）设计讲解，用户标记"重点圈起来"
> 读者：agent 开发小白（有 Java 背景）
> 核心一句话：**工具执行前给插件一个"短路决策点"——插件返回非 None 就拦截，拦截值作为工具结果回填给模型**

---

## 1. 问题：模型要调工具时，系统怎么安全介入？

agent 循环里，模型（LLM）通过 tool_calls 发起工具调用。安全介入的困境：

```
❌ 直接不执行 + 什么都不说 → 模型看到"工具调用没有结果"→ 困惑重试 / 崩溃
❌ 直接中断整个对话       → 一个工具失败毁掉整轮对话（违反"工具失败不中断循环"原则）
❌ 拦截逻辑写死在循环里   → 每加一种防护（安全/审批/限流）都要改 agent.py
✅ 拦截 + 给模型一个"可行动的文本结果" → 模型理解并调整策略，循环继续
```

## 2. 设计：`agent/tool-call` 事件用 bail 分发

```python
# agent.py（主循环内，每个工具调用前）
decision = self.events.bail(
    "agent/tool-call",
    name=call.name,          # 工具名
    arguments=call.arguments,  # 参数
    turn=self._turn, step=step,
)
if decision is not None:
    output = str(decision)   # 拦截：用返回值作为工具结果
    duration = 0.0
else:
    output = execute_tool(call.name, call.arguments)  # 放行：正常执行
```

**bail 语义**（Cordis 三分发之一）：按 priority 询问所有监听者，**第一个返回非 None 的生效，后面的不用问**。

```
模型想调 shell("rm -rf /")
    │
    ▼
问统计插件（priority=100）→ 记时间，返回 None（"没意见"）
    │
    ▼
问安全插件（priority=200）→ 检测到危险 → 返回 "[安全拦截] 命令包含危险操作" → 停！
    │
  后面的插件不用问了
    │
    ▼
工具【不执行】→ 拦截值作为 tool 结果回填给模型
    │
    ▼
模型（读到结果）→ "抱歉，我无法执行删除系统目录的操作。"
```

## 3. 为什么这个设计巧妙（四个层面）

### ① 拦截而不中断：循环永远有"结果"可读

模型只能看到文本。拦截值**冒充工具结果**回填，保证：
- 循环正常继续（不崩溃、不中断）
- 模型拿到"调用有响应"的完整协议体验

### ② 信息可行动：拦截消息是给模型的"纠错信号"

与 `[参数错误]`（v0.4.7）同一原则：**所有回填给模型的信息都要可行动**。
模型看到拦截原因，能自己调整：换工具 / 放弃 / 向用户解释。

### ③ 防线可插拔：加一个插件，所有工具立刻有审核

拦截逻辑不在主循环里，在插件里：
- 加安全插件 → 所有工具自动过审
- 删安全插件 → 行为回到原样
- **agent.py 一行不改**

### ④ 决策链按优先级：多个决策插件共存不打架

`priority` 决定询问顺序：安全 > 审批 > 统计。每个插件只需回答"我有意见/没意见"，
不需要知道其他插件的存在——标准的责任链（Chain of Responsibility）。

## 4. 回填协议（拦截值的"格式要求"）

拦截值必须是**给模型看的可行动文本**，约定：

| 前缀 | 语义 | 模型看到后的行为 |
|------|------|-----------------|
| `[安全拦截]` | 红线，不可执行 | 换工具 / 放弃 / 解释 |
| `[参数错误]` | 传参有误（可修正） | 修正参数重试 |
| `[审批]` | 需要用户确认 | 转去询问用户 |
| `[工具错误]` | 工具本身失败 | 换工具 / 放弃 |

前缀分类让模型能**分类决策**（这正是参数校验方案里 `[参数错误]` 前缀的设计延伸）。

## 5. 与 Hermes 对照（业界做法）

| 维度 | qi-agent（事件化） | Hermes（approval.py） |
|------|-------------------|----------------------|
| 拦截点位置 | 事件总线（可插拔） | 工具执行路径内的检测模块 |
| 扩展方式 | 加插件（install 注册） | 改/扩 approval.py（硬编码模块） |
| 决策方式 | 插件返回文本（bail） | 模式检测 + 交互弹窗 + 辅助 LLM 智能审批 |
| 状态管理 | 无（当前） | 会话级审批状态 + allowlist 持久化（config.yaml） |
| 借鉴点 | — | 辅助 LLM 自动批准低风险命令、allowlist 持久化（后续 TODO） |

**结论**：我们的 bail 设计在"可插拔"上更优（事件总线解耦）；Hermes 在"审批体验"上更完整
（会话状态、智能审批、持久化白名单）——两者是未来 shell 三档权限升级的互补参考。
