# 子任务轮询进度与终态渲染

## 这次要解决什么

这次修复的是 Web 界面里“子任务卡片”的一整条链路，不只是一个样式问题。

用户实际看到的症状有四类：

1. 子任务明明已经有结果，卡片还是一直停在“运行中”
2. 完成后的结果默认折叠，用户要多点一次才能看到真正交付物
3. `need_more_info`、`stopped` 这类终态会继续轮询，最后被 60 秒超时兜底吞掉
4. 进度事件有到达，但轮询元数据被错误清掉后，卡片无法续命，只能静默死亡

所以这次不是“把 UI 画漂亮一点”，而是把子任务的状态机、轮询生命周期和前端展示规则重新对齐。

## 先说原理

子任务界面本质上有三层信息：

1. **终态信息**：这个子任务最后是成功、失败、需要补充信息，还是被停止
2. **过程信息**：执行过程中发生了什么，工具调用了什么，进度怎么推进
3. **展示信息**：用户第一次看卡片时，应该先看到什么，哪些内容需要展开

这三层不能混在一起。

如果把“进度”和“终态”都塞到一个字段里，前端会出现两个典型问题：

- 轮询线程会把展示状态误当成执行状态
- 执行状态一变化，前端又把历史过程覆盖掉

所以这次修复的核心原则是：

- **轮询只负责探测状态**
- **进度列表只负责记录过程**
- **卡片展示只负责决定默认视图**

这和 Hermes 里常见的做法是一样的：执行引擎负责发事件，UI 负责消费事件，UI 自己不要再去“推导”执行真相。

## 为什么要把 timer 和 meta 分开

之前的 bug 不是“没有定时器”，而是**定时器生命周期和轮询元数据生命周期绑死了**。

正确理解应该是：

- `timer` 只是“下一次什么时候去问一次”
- `meta` 是“这个子任务上次状态是什么、多久没变化了”

这两个东西不是一回事。

如果每次 `scheduleSubTaskPoll()` 都顺手清掉 meta，就会发生这种链路：

1. `startDelegate()` 创建子任务 entry 和 meta
2. 立刻 `scheduleSubTaskPoll()`
3. 旧实现把 meta 清掉
4. 2 秒后轮询开始，发现 meta 不见了
5. 直接返回，轮询链路死亡

这就是“子任务完成了，但卡片一直在运行中”的根因之一。

这次修复把它拆成了两层：

- `clearSubTaskTimer()`：只停定时器
- `clearSubTaskPoll()`：只在真正结束时，才连 timer 和 meta 一起清掉

这样轮询重排不会误删状态，状态真正结束时也能一次性释放资源。

## 为什么要允许从 entry 恢复 meta

这个修复点看起来像“补一个兜底”，其实是恢复能力。

前端的子任务列表 entry 本身就是一份可恢复快照：

- 目标是什么
- 当前状态是什么
- 进度有哪些
- 结果和原因是什么

如果 meta 暂时丢了，但 entry 还在，说明“展示态还在，轮询态断了”。
这时最合理的做法不是直接放弃，而是从 entry 重建 meta 继续轮询。

这相当于把前端状态做成了一个轻量的 checkpoint。

工业里更成熟的系统会把这个 checkpoint 放到 store、数据库或 session state 里。
当前项目是单用户本地场景，所以这里采用的是：

- `entriesRef` 作为重建依据
- `subTaskMetaRef` 作为短期轮询状态

这比“状态丢了就算了”强很多，但没有过度设计成持久化存储。

## 为什么终态要扩展到 `need_more_info` 和 `stopped`

之前轮询只认 `completed` 和 `failed`，这会把真实业务语义抹掉。

但实际上，子任务不只有“成功/失败”两种结果，还会出现：

- `need_more_info`：任务需要用户补充信息，当前不能继续硬跑
- `stopped`：任务被显式停止，应该立即收口

这两种都不是“继续轮询看看会不会突然变成功”的状态。

如果不把它们当终态：

- 前端会继续问后端
- 直到超时
- 最终卡片显示的不是“需要补充信息”，而是“60 秒无变化”

这会把真正的业务结论盖掉。

所以这次把它们纳入终态集合，并且在终态渲染时：

- `completed` 默认展开全文
- `failed` 显示失败原因
- `need_more_info` 显示摘要 + 问题
- `stopped` 显示停止原因

这才符合“终态应该一眼看懂”的原则。

## 为什么 completed 要默认展开

这个点是产品语义，不是代码技巧。

对于子任务来说，真正的交付物是结果，不是过程。
所以完成态卡片默认应该让用户看到完整结果，而不是让用户先去点“展开”。

只有当结果特别长的时候，才需要折叠。

这次采用的规则是：

- 结果长度不长时，默认展开
- 结果长度超过阈值时，默认折叠，只展示前 300 个字符
- 用户点击后可以看完整结果

这样做的好处是：

- 正常完成态的关键信息不被藏起来
- 特别长的输出不会把页面撑爆
- 用户仍然保有完整查看能力

这里的阈值是工程裁剪，不是绝对真理。以后如果子任务结果类型更丰富，可以再按“结构化结果优先、纯文本兜底”的方式继续升级。

## 为什么进度只保留最近 50 条

进度条是过程日志，不是永久档案。

如果不做上限，长任务会把前端内存和渲染压力慢慢堆高。
所以这次做了一个明确裁剪：

- 运行中的进度列表最多保留 50 条
- 卡片里只展示最近 5 条
- 如果还有更早的记录，用省略提示说明存在历史内容

这样做的逻辑是：

- UI 要可读
- 内存要可控
- 过程信息要“够用”，不是“无限保存”

这是典型的前端工业化裁剪：不追求把所有历史都塞进一个卡片，而是控制展示密度。

## 和后端事件转发的关系

这次前端修复之所以能成立，是因为后端已经把子上下文事件分流成了两条路径：

- 主上下文事件继续走原有 `item/toolCall`、`item/toolResult`、`turn/end`
- 子任务进度单独走 `item/subtaskProgress`

这件事很关键。

因为 UI 如果只盯着轮询，就只能知道“现在是什么状态”；
如果能同时收到进度事件，就能知道“中间发生了什么”。

这也是当前实现和很多工业系统的共同点：

- 状态查询负责最终一致性
- 事件推送负责过程可见性

两者一起用，用户体验才不会只剩“转圈”和“结果页”。

## 工业级落地考量

- **可靠性**：做了。轮询与 meta 分离、终态收口、meta 可从 entry 恢复、进度做上限，都是为了减少死链和无限增长。
- **安全**：裁剪。这里没有新增权限或凭证流，子任务进度只展示摘要，不把完整敏感上下文当通知内容原样扩散。
- **记忆**：裁剪。当前只做会话内可恢复，不把子任务轮询状态持久化到数据库；这是单用户本地场景下合理的复杂度控制。
- **可观测**：做了。保留 `console.debug` 的轮询诊断、后端 `item/subtaskProgress` 事件和测试用例，方便以后按日志回放排查。

## 这次的设计取舍

1. **做了**：终态扩展、进度裁剪、默认展开、meta 恢复。
2. **没做**：持久化子任务状态、服务端订阅重放、复杂的富文本结果渲染。
3. **原因**：当前场景是单用户 Web UI，本次问题本质是生命周期错配，不是存储系统缺失。

如果以后要做多会话、多端同步或者断线恢复，这一层就应该升级成真正的子任务状态仓库，而不是继续在前端 ref 上叠补丁。
