# 11 approved 绕过教训：放行通道引入后，拦截层必须三层同步

> 归档：2026-08-20 · 来源：v0.4.21 审批档边界调整（实现时发现的安全漏洞）
> 读者：agent 开发小白（有 Java 背景）
> 关联：docs/plans/2026-08-20-审批档边界调整方案.md（2.5 节）、principles/08（bail 拦截）
> 核心：**任何"放行通道"的引入，都必须审计所有拦截层是否会被绕过**

---

## 1. 事故还原：format 差点变成"可审批执行"

v0.4.21 调整审批边界时（用户决策：format/shutdown 等红线不可执行），
发现一个**分层漏洞**：

```
漏洞场景：
  format C: 原在审批档（_APPROVAL_PREFIXES 有 "format "）
  → NEED_APPROVAL → 用户同意 → agent 注入 approved=True
  → shell 工具执行——但 approved=True 会【跳过工具层硬拒检查】！
  → format 真的执行了！？

为什么：
  硬拒（_DANGEROUS_KEYWORDS 含 format）只在 shell 工具层
  审批同意路径（approved=True）跳过工具层检查（设计如此——用户已批准）
  → 工具层硬拒被 approved 绕过
```

**本质**：安全体系分了三层（工具层硬拒 / 插件层判档 / agent 层注入），
但"红线"只存在于其中一层——其他层的放行通道（approved）把它绕过了。

## 2. 修复：红线必须在插件层也生效

```
_HARDLINE_PREFIXES = (format, mkfs, dd, shutdown, reboot)

security_guard._on_tool_call 判定顺序：
  ① 用户黑名单 → 硬拒
  ② 敏感路径 → 硬拒
  ③ 红线前缀（_HARDLINE_PREFIXES）→ 硬拒（【新增】——先于审批档）
  ④ 审批档（_APPROVAL_PREFIXES）→ NEED_APPROVAL
  ⑤ 放行

红线在 ③ 直接拦截 → 永远不产生 NEED_APPROVAL → 永远不会有 approved
→ approved 绕过路径被切断 ✅
```

**三层同步原则**：
```
红线（不可审批）必须在【所有】有"放行能力"的层都生效：
  工具层：硬拒（approved=False 时兜底）
  插件层：直接拦截（不产生审批——防 approved 注入）
  （agent 层：只认 NEED_APPROVAL 标记，红线不产生标记）
```

## 3. 通用教训（为什么重要）

**任何"放行通道"（approved / 白名单例外 / 免审清单）引入后，必须审计
所有拦截层是否会被绕过**——这像权限提升审计：

```
类比：大楼安保分三层（大门门禁 / 楼层闸机 / 房间门锁）
  "红线房间"（金库）只在房间门锁拦截
  但审批通道（经理卡）能开所有门 → 金库失守
  修复：金库在大门门禁就标记"禁止通行"（任何卡都不放行）
```

**审计清单**（引入新放行通道时逐项问）：
1. 红线在哪几层有拦截？（工具层 / 插件层 / agent 层）
2. 放行通道（approved 等）会跳过哪些层？
3. 红线是否在所有被跳过的层都有独立拦截？

## 4. 对照 Hermes

Hermes approval.py 的 `detect_hardline_command` 在**审批系统内部**直接拒绝
（`_hardline_block_result`）——红线检查发生在审批判定本身，天然不会
产生审批请求（与我们的 _HARDLINE_PREFIXES 先于审批档检查同构）。
Hermes 源码注释也强调 hardline "cannot be executed via the agent —
not even with --yolo"——红线不可被任何放行模式绕过（业界共识）。

## 5. 一句话总结

**放行通道是给"可审操作"开的门；红线必须在门的另一侧也有守卫——
否则"审批同意"就是绕过红线的合法路径。**
