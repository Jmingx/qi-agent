## 1. L3 评测：怎么让真实对话触发压缩（关键设计）

### 问题

压缩阈值 = 窗口 × 阈值 = 128K × 0.7 = 89.6K token。30 轮普通对话只有 5-10K token——**真实对话永远触发不了压缩**。

### 解决：任务级配置覆盖（plugin_overrides）

```
EvalTask 新增字段：
  plugin_overrides：任务级插件配置覆盖（build_agent 深合并进 plugins.toml 配置）
  setup：任务前置回调（跑 steps 前执行）

c-long-1 的覆盖：
  context_manager.compress = {window: 2000, threshold: 0.5}
  → 1000 token 即触发压缩——20 轮对话轻松超
  async_compress = False（同步压缩，评测确定性）
```

**设计哲学**：小窗口验证的是"**压缩机制本身**"（触发→摘要→事实保持），不是"撑爆真实窗口"。真实窗口下的行为由小窗口外推（同一条代码路径）。

### 为什么 plugin_overrides 要深合并

```
配置结构：context_manager = {chain, compress: {window, threshold}, async_compress}
浅合并 {**base, **override}：override 的 compress 会整体替换 base 的 compress
  → base 的其他 compress 字段（keep_recent 等）丢失
深合并（递归）：只覆盖同名键，其余保留
```

```python
def _deep_merge(base: dict, override: dict) -> dict:
    result = dict(base)
    for key, value in override.items():
        if isinstance(value, dict) and isinstance(result.get(key), dict):
            result[key] = _deep_merge(result[key], value)  # 递归
        else:
            result[key] = value
    return result
```

## 2. L3 任务设计（4 个）

| 任务 | 验证什么 | 怎么验证 |
|---|---|---|
| c-long-1 | 压缩后**事实保持** | 20 轮穿插"猫叫咪咪"→压缩→问→答含"咪咪" |
| c-long-2 | **sticky** 压缩后仍在 | setup 注入 sticky"小Q"→压缩→问名字→答含"小Q" |
| c-long-3 | 压缩后**不重做** | setup 建 todo"写周报"→压缩→问→答含"周报" + todo 工具未再调用（forbidden_tools） |
| c-long-4 | **L4 一致性对比** | 压缩前/后各问一次→"咪咪"出现 ≥2 次（expected_keyword_min_count） |

**forbidden_tools**（judge 扩展）：期望未调用的工具——c-long-3 验证"模型从摘要读 todo 内容直接回答，而不是重新调用 todo 工具创建"（不重做）。

**expected_keyword_min_count**：关键词在【所有】assistant 回答中出现 ≥N 次——L4 的"压缩前 1 次 + 压缩后 1 次"。

## 3. C3 压缩模型独立配置（make_summarizer 工厂）

```python
def make_summarizer(model: str | None = None) -> callable:
    """摘要器工厂：None = 复用主模型；指定 model = 独立压缩模型。"""
    def summarizer(messages):
        client = LLMClient(load_api_key(), model=model or "deepseek-v4-flash")
        return client.chat([...摘要提示...]).content
    return summarizer

# 插件读取配置：
compress_cfg = config.get("compress", {})
self._summarizer = summarizer or make_summarizer(compress_cfg.get("compression_model"))
```

**为什么用工厂而不是直接传模型名**：摘要器是"可注入依赖"（测试 mock 注入），
配置是"运行时数据"。工厂把"配置→可调用"的转换收敛一处——测试注入 mock
（绕过工厂），真实路径工厂读配置（零侵入）。

**惰性**：client 在首次调用才创建——不压缩不烧 token。

## 5. 踩过的坑

1. **C3 改造破坏旧测试**：context_manager 从 `default_summarizer` 换成
   `make_summarizer` 工厂——`test_async_compressor` 的 monkeypatch 目标
   （`context_manager.default_summarizer`）过时 → AttributeError。
   教训：**改 import 后全量搜 mock/monkeypatch 的模块路径**。
2. **函数内 import 的 patch 位置**：`make_summarizer` 内部
   `from qi_agent.llm import LLMClient`——patch 目标是 `qi_agent.llm.LLMClient`
   （模块属性），不是 `compressor.LLMClient`（compressor 模块没有这个属性，
   函数内 import 每次执行从源头模块取）。
3. **"12→12"假象**：验收时消息数没降——不是没压缩，是早期只有 1 组消息
   压缩成 1 条摘要块（数量巧合）。**验证压缩要看摘要是否生成 + 早期组是否
   被替换**，不能只看消息数。

## 6. L3 首跑实测教训（真实 LLM 暴露的 3 个问题）

**① 压缩过频导致链式退化（最重要）**：小窗口 2000 时 20 轮对话触发 10+ 次
压缩——每次压缩把"上次的摘要块 + 新历史"再摘要（**摘要的摘要**），
细节逐层丢失（c-long-1 的"猫叫咪咪"在第 1 轮，经多次再摘要后消失，
模型答"你好像从来没提过养猫"）。**修复**：窗口调大到 6000（触发 1-2 次）。
产品启示：默认 128K 窗口压缩频率极低（~90K token 一次），链式退化风险小；
但**压缩后应立即停止再压缩**（现有防重复逻辑已覆盖切换后跳过 compress）。

**② 全局态并发污染**：sticky 是进程级单例（`_STICKY` 全局 list）——
c-long-2 的 setup `remember("用户叫小Q")` 注入后，**并发的** c-long-1 的
agent 第一轮 pre-step 也挂载了"小Q"（回答里出现"小Q，你好像没提过养猫"）。
**修复**：有 setup 的任务在 runner 里**串行执行**（全局态隔离），
无 setup 的任务保持并发。教训：**评测任务有全局态副作用时必须串行**。

**③ 超时不足**：并发 + 频繁压缩调用（每次压缩一次真实 LLM 摘要调用）
导致 c-long-2/3 超时。**修复**：串行（独占 API 带宽）+ 超时放宽 360s。
