# 07 事件驱动与钩子原理：agent 插件化的地基概念

> 归档：2026-08-18 · 来源：qi-agent 插件化方案讨论问答
> 读者：agent 开发小白（有 Java 背景）
> 定位：项目架构设计的基础概念——"一切皆插件"（DSH 架构）的两个核心机制

---

## 1. 为什么聊这个

讨论 qi-agent 插件化架构时，必须先分清两个常被混用的概念：**钩子（Hook）** 和 **事件驱动（Event-Driven）**。用户敏锐地发现："事件化应该是事件驱动，但你描述的像是在循环里实现钩子"——这个观察是对的。本文件把两者讲透，再讲 DSH（deepseek-harness）如何用一套机制统一它们。

## 2. 钩子（Hook）：主流程在固定点"拉"外部代码

### 2.1 定义

**钩子 = 主程序在代码路径的固定位置调用注册进来的回调，等待返回值，用返回值影响主流程。**

特征：
- 主流程**主动调用**外部代码（拉的模式）
- **同步、线性**：走到钩子点 → 等回调返回 → 继续执行
- 回调的**返回值能改变主流程**的数据、行为、甚至决策
- 主流程知道钩子点在哪（耦合点是"位置"）

### 2.2 Java 类比

- **模板方法模式（Template Method）**：基类骨架固定，`abstract` 方法由子类实现，基类在固定位置调用
- **回调接口（Callback）**：`interface Callback { String apply(String arg); }`，主程序持有并调用

### 2.3 真实例子

- pytest 的 `hookspec/hookimpl`（pluggy）
- git 的 pre-commit / post-commit hook
- Spring 的拦截器（Interceptor）

### 2.4 代码形态

```python
# 主循环的固定位置
while True:
    resp = llm.chat(messages)
    # ← 钩子点：插件可以在这里审查/改写 resp
    for hook in registered_hooks:
        resp = hook(resp)   # 返回值影响后续逻辑
```

## 3. 事件驱动（Event-Driven）：发布-订阅，"推"给所有关心者

### 3.1 定义

**事件驱动 = 系统组件通过"发布消息 / 订阅消息"解耦协作。发布者不认识任何监听者，监听者只对感兴趣的事件做出反应。**

特征：
- 发布者**广播消息**，不关心谁在听（推的模式）
- 发布者与监听者**零耦合**（互相不知道对方存在）
- 通常**异步、非阻塞**：发完消息就继续，不等监听者
- 监听者**改不了发布者的数据**（单向通知）
- 事件流驱动系统运转（GUI 点击 → 处理函数）

### 3.2 Java 类比

- **观察者模式（Observer）**：`Observable` 维护监听列表，`notifyObservers()` 广播
- **消息队列**：Kafka / RabbitMQ——生产者发消息到 topic，消费者订阅，双方完全隔离

### 3.3 真实例子

- GUI 编程（按钮点击事件、窗口关闭事件）
- Node.js `EventEmitter`
- 浏览器 DOM 事件（click/scroll/keydown）
- 微服务间的消息总线

### 3.4 代码形态

```python
# 发布者：完全不认识监听者
bus.publish("user_login", user_id=42)   # 发完就继续，不等任何人

# 监听者：只关心自己订阅的事件
@bus.subscribe("user_login")
def send_welcome_email(user_id):
    ...
```

## 4. 两者本质区别（一张表）

| 维度 | 钩子（Hook） | 事件驱动（Event-Driven） |
|------|-------------|------------------------|
| 调用方向 | 主流程**主动调用**外部（拉） | 发布者**广播**，监听者订阅（推） |
| 耦合 | 主流程知道钩子点，回调注册进固定位置 | 发布者**完全不认识**监听者 |
| 时序 | 同步、线性（等待返回） | 通常异步、非阻塞 |
| 数据流 | **返回值影响主流程**（可改数据/决策） | 单向通知（fire-and-forget） |
| 控制权 | 在主流程手里（它允许你介入） | 在事件流手里（消息到哪，谁处理） |
| Java 类比 | 模板方法 / 回调接口 / SPI | 观察者模式 / 消息队列 |
| 典型场景 | pytest 插件、git hook、拦截器 | GUI、EventEmitter、Kafka |

**一句话**：钩子是"主流程开的口子，外部代码进来参与决策"；事件驱动是"消息到处流，谁关心谁听"。

## 5. 为什么 agent 循环里需要的主要是钩子

agent 主循环是**单线程顺序执行**，且**必须等外部代码的返回值来决定下一步**：

```python
while True:
    resp = llm.chat(...)
    if resp.tool_calls:
        for call in resp.tool_calls:
            # 审批插件说"拒绝" → 循环必须停下来/改走其他路径
            # 统计插件要记录这次调用 → 必须在执行前/后拿到数据
            output = execute_tool(call.name, call.arguments)
```

关键：**同步 + 有返回值**。严格的事件驱动（发完就继续跑）做不到"等待决策"，所以 agent 循环的扩展点本质是**钩子语义**。

## 6. DSH 的答案：一套事件总线，五种分发模式，统一两者

DSH（deepseek-harness）vendored 的 Cordis 框架，核心是一套事件总线接口 + 五种分发模式，覆盖从"纯事件"到"纯钩子"的完整谱系：

| 分发模式 | 语义 | 典型用途 |
|---------|------|---------|
| `emit` | 广播通知，不关心返回值（fire-and-forget） | `agent/status` 状态变化 → 通知 UI |
| `parallel` | 并行执行所有监听者 | 互不依赖的统计任务 |
| `serial` | 串行执行，可短路停止 | 有顺序依赖的副作用 |
| `bail` | 第一个非 None 返回值就停 | 快速决策（谁先给答案听谁的） |
| **`waterfall`** | **前一个监听者的返回值作为下一个的输入，最终结果回传发布者** | `agent/pre-step`：插件改写消息、拒绝 step |

**关键认知**：`agent/pre-step` 用 waterfall 本质就是"事件总线实现的钩子"——它叫事件（注册接口统一为 `ctx.on(name, fn)`），但语义是钩子（同步、有返回值、影响主流程）。而 `agent/status` 用 emit 是纯通知。**成熟系统两者都要**，同一套接口按分发模式切换。

## 7. pluggy 是什么（pytest 的插件系统）

**pluggy = pytest 的插件机制**（pytest 团队维护）。核心两个装饰器：

```python
# 主程序声明扩展点
@hookspec
def my_hook(arg: str) -> str: ...

# 插件实现扩展点
@hookimpl
def my_hook(arg: str) -> str:
    return arg.upper()
```

特性：
- 按注册顺序调用所有实现
- `firstresult`：第一个非 None 结果短路返回
- `hookwrapper`：钩子执行前后包一层（中间件模式）
- `tryfirst/trylast`：控制执行顺序
- 注册来源：`setuptools entry_points`（第三方包安装即注册）

**Java 类比**：≈ `ServiceLoader`（SPI）+ 回调接口。

**局限**：只有同步钩子语义，没有事件总线（无 topic 广播、无异步）。对单项目而言 entry_points 机制偏重——这正是 qi-agent 自研轻量总线（~80 行）的理由。

## 8. 对 qi-agent 的启示（档位 A 设计依据）

1. **扩展点用"钩子语义"**：同步、有返回值、影响主循环——这是 agent 循环的硬需求
2. **接口统一，分发模式区分**：`emit`（通知：状态/统计）+ `waterfall`（改写：pre-step）+ `bail`（决策：工具审批）三种起步即可，`parallel` 延后（单线程不需要）
3. **无插件零影响**：事件点没有监听者时直接跳过，行为与现在完全一致（向后兼容）
4. **这是全插件化（档位 C）的第一块地基**：将来容器/生命周期/作用域都在这个事件总线之上生长
5. **对照 DSH 事件命名**：`agent/turn-start`、`agent/pre-step`、`agent/tool-call`、`agent/final-answer`——与 DSH 同名同语义，将来对照源码学习无障碍
