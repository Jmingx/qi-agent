# 并发问题深度复盘（面试亮点材料）

日期：2026-08-29
定位：面试难点回答素材 + 经验沉淀——"我在自己的 Agent 框架里解决并发问题的完整叙事"
用法：面试被问到"并发/多线程/架构设计"时，按本文第三、四节的框架组织回答

---

## 一、一句话概括（面试开场用）

> "我在自研的 Agent 框架（qi-agent）多线程化演进中，系统性地解决了并发问题。核心认知是：**并发 bug 不来自线程本身，而来自共享可变状态；解决方案不是到处加锁，而是'设计掉共享'——通信走队列、状态定所有权、读取走快照。**"

## 二、背景故事（STAR 的 Situation & Task）

自研 Agent 框架演进经历三个阶段：
1. **单线程时代**：主线程跑 agent 循环（LLM 调用 + 工具执行），一切状态天然串行——代码里全是无锁的共享可变状态（消息列表、指令队列、状态字段），单线程下安全，没人加锁
2. **多线程化演进**（关键转折）：为支持实时中断、多 agent 并发、后台记忆提炼、网关层，引入多个线程——后台 chat 线程（不等 LLM 可实时 /stop）、AgentPool（Semaphore 限并发）、提炼线程（每 10 轮后台提炼记忆）、持久化线程（write-behind）
3. **问题爆发**：演进中只给"调度入口"加了锁（manager 锁、存储锁），**数据本身还是裸的**——并发问题集中爆发

**真实事故（面试加分项——有血有肉的细节）**：
- **审批弹窗抢输入**：审批弹窗时用户输入被主线程抢走 → 同一 context 并发 run → 消息交错 + HTTP 400 + KeyError（已踩）
- **sticky 串味**：评测 3 个 agent 并发时，模块级单例（todo 存储）互相污染，agent 的回答串味（"小Q"注入到了别的会话）
- **流式 usage 拿不到**：DeepSeek 流式下 usage 大部分不返回，缓存命中率观测链路断

## 三、核心分析框架（面试主体——这是亮点所在）

### 3.1 关键认知：并发问题的判据

**变量独立 ≠ 线程独占**——判据是"有几个线程碰它"，不是"变量是否独立"：

```
单线程独占（只有一个线程读写）→ 安全（哪怕变量复杂）
多线程共享（多个线程都读写）→ 竞态（哪怕只是一个字段）
```

实例：`status` 一个字段（够独立吧？）——worker 线程 `if RUNNING: status=COMPLETED` + 控制线程 `if RUNNING: status=STOPPED`，读-判-写交错 → 后写覆盖先写 → 状态机不一致（任务被停却显示完成）。

### 3.2 问题分类：两类问题，两套解法

```
┌─ 通信类：线程要【通知】另一线程 ──→ 消息队列化
│    提炼完成要告诉主线程 / 流式增量要发给外壳
└─ 共享状态类：线程要【读写同一份数据】──→ 少共享（队列化结构/锁/快照）
      steer_queue 竞态 / 审批表竞态 / status 写竞争
      ——不是 emit，改消息队列没用
```

**这是最核心的洞见**：很多人把所有并发问题都归为"加锁"——实际要先分类：通信问题用队列（无锁），共享状态问题才用锁/所有权。

### 3.3 三类具体竞态（各配一个"机制级"解释）

| 竞态 | 机制 | 为什么是问题 |
|---|---|---|
| **指令队列竞态**（steer_queue） | `copy+clear` 两步非原子：控制线程 append 与 worker 线程 clear 交错 → 新指令被误清 | 控制面失效——父 agent 让子 agent"改方向"，指令永久丢失，agent 继续错方向跑（不是"脏数据"，是"命令没送达"） |
| **状态机写竞争**（status） | 两个线程都"读-判-写"同一字段 → 后写覆盖先写 | 非法状态组合——被停的任务显示完成，行为不可信 |
| **审批表竞态**（gateway） | `len+1` 生成 id 非原子 → 两个并发审批撞号 → 后写覆盖先写 | 审批串线——A 的审批结果由 B 的响应决定；无锁 dict 并发读写 |

### 3.4 解决方案：三件套

```
① 通信走队列：事件总线保持单线程语义（同步/有序/无锁，不为并发付费），
   跨线程通知用独立消息队列（每 agent 一个邮箱——对齐 DSH inbox / A2A 邮箱，
   actor 模型思想：通信走消息，不共享）
② 共享状态少共享：
   - steer_queue：list → queue.Queue（put/get 原子，1 行消灭竞态）
   - 审批表：uuid 生成 id + 锁
   - status：所有权声明——归执行线程独占写，stop 只 set 标志由循环线程转换
   （锁是最后手段；优先用"队列化数据结构"和"所有权声明"）
③ 读取走快照：后台任务（持久化/提炼）先同步取快照副本，只碰副本不碰 live 状态
```

**边界判断（面试官追问点——展示深度）**：
- 哪些不能异步化：**waterfall/bail 协议事件**（pre-step 瀑布依赖 handler 返回值修改消息——队列化就断了）——所以"选择性异步"：通知类 emit 可队列化，协议类必须同步
- 哪些不能"脏数据可接受"：**压缩写回**（改的是模型可见状态 messages——脏 = 缓存整段失效 50 倍价差 + 角色交替破坏 + 400 错误）——所以压缩"后台计算 + 循环内原子切换"（异步算、同步写回）

## 四、业界对照（面试"你怎么知道这是对的"）

| 我的方案 | 业界对应 |
|---|---|
| emit 单线程专用 + 线程间消息队列 | **Node.js**：EventEmitter 同步单线程 + worker_threads postMessage |
| 事件循环 + 队列消费 | **Hermes**：asyncio 事件循环（emit 只在循环线程，后台线程 queue 回传） |
| 每 agent 一个邮箱队列 | **DSH** inbox（每 agent jsonl 收件箱）/ **A2A** 邮箱 / **actor 模型**（Erlang/Akka） |
| 设计掉共享而非加锁 | **Redis** 单线程事件循环 10 万 QPS（无锁）、**Reactor 模式**（Doug Lea） |
| 后台算 + 同步切换 | **DSH** AsyncCompressor / Hermes context compression 同款 |

## 五、面试回答框架（60-90 秒版）

```
① 结论先行：并发 bug 来自共享可变状态，解法是"设计掉共享"
② 一个事故证明认知：审批弹窗抢输入 → 同 context 并发 run → 消息交错 400
③ 分类框架：通信类（队列化）vs 共享状态类（少共享）——不是都加锁
④ 三个机制级细节：steer_queue copy+clear 竞态、status 读-判-写竞争、
   审批表 len+1 撞号——证明真懂不是背概念
⑤ 边界判断：waterfall/bail 不能异步（协议依赖返回值）；压缩不能脏写
   （模型可见状态）——证明有工程判断力
⑥ 业界对照：Node.js EventEmitter + postMessage、DSH inbox、actor 模型
   ——证明有广度
```

## 六、可以继续深入的点（面试官深挖时）

1. **Reactor/事件驱动模型**：Node.js 单线程事件循环、Netty 主从 Reactor、Redis 无锁 10 万 QPS——"设计掉共享"的极致形态；我的 gateway 传输层计划用 asyncio 落地
2. **快照隔离 vs 锁**：读多写少场景快照（copy-on-read）优于锁；write-behind 与"崩溃丢尾可接受"的取舍
3. **Python GIL 下的真实线程安全**：list.append 原子但"检查-操作"不原子；queue.Queue 内部 Condition；threading.Event 天生线程安全——Python 并发要懂"哪个原语原子"
4. **状态机与并发的关系**：状态机转换必须是唯一入口（stop = 转换不是 flag 乱改）——状态机一致性是并发安全的另一半
5. **进程级 vs 线程级**：线程级消息队列（BlockingQueue）vs 进程级（RabbitMQ/Kafka）vs agent 间（A2A）——同族思想不同层级

## 七、一句话收尾（面试结束语）

> "这次并发改造让我建立了'少共享、多队列、定所有权'的并发设计直觉——比背锁的知识更有价值，因为它适用于从单机多线程到分布式系统的一致设计原则。"
