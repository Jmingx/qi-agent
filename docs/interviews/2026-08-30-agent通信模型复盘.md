## 一、一句话概括（面试开场用）

> "我在自研 Agent 框架中，把 agent 间通信从'散装通道'收敛成**统一邮局模型**（消息代理模式）：每个 agent 一个邮箱，消息统一走中央队列由 Dispatcher 线程路由——**通信与执行解耦、同步与异步统一、为未来 A2A 协议预留接口**。"

## 二、背景故事（STAR 的 Situation & Task）

自研 Agent 框架（qi-agent）支持主 agent + 子 agent（delegate 任务）：

**初始状态（问题）**：agent 间通信是"散装通道"——steer 一个队列、结果一个回调、通知一个事件，各管各的：
```
父 → 子（多轮指导）：直接调子 context 的方法（耦合！）
子 → 父（结果回传）：回调 + 结果字段（双通道）
控制指令：又一个独立队列
→ 通道越来越多、语义混乱、无法统一审计、跨线程竞态频发
```

**任务**：设计统一的 agent 通信模型——同时为未来 A2A（agent 间协议）预留扩展。

## 三、设计过程（STAR 的 Action——展示思考链，面试主体）

### 第 1 步：从"邮局"到"消息代理"（用户主导的架构演进）

```
最初方案（v2）：每 agent 一个 mailbox（收件箱）
  → 但"谁负责投递"不清晰——agent 自己调 Dispatcher.send（路由耦合在 agent）

演进（v3）：消息代理模式
  → agent 只做两件事：send（丢自己邮箱）+ drain（取自己邮箱）
  → Dispatcher = 独立线程的消息代理（路由注册 + 投递）
  → agent 与路由完全解耦
```

### 第 2 步：核心难题——"多队列监听"（面试亮点：多路复用）

```
问题：Dispatcher 要监听 N 个 agent 的 outbox 队列——怎么高效？
  · 轮询 N 队列：空轮询浪费 CPU（N 大是瓶颈）
  · 单线程阻塞等多个队列：卡死（等一个就看不到另一个）
  · epoll？——只能监听 FD（socket/pipe），监听不了内存队列！

关键洞察（我的方案）：不要监听 N 个队列——让所有消息【汇聚到一个队列】！
  → 所有 agent 的 outbox 都【引用同一个中央队列】（register 时绑定）
  → Dispatcher 只阻塞等一个队列（get——零轮询 + FIFO 顺序）
  → 多路复用问题消失

类比：Kafka topic（汇聚）+ 消费者组（分发）——消息代理的标准答案
```

```
graph LR
    A["outbox A = central 引用"] --> C["中央队列"]
    B["outbox B = central 引用"] --> C
    D["outbox C = central 引用"] --> C
    C --> E["Dispatcher 阻塞 get（零轮询）"]
```

### 第 3 步：消息/状态分离（双通道设计——面试亮点：不为并发付费）

```
两条通信通道，各司其职：
  事件总线（EventBus）＝ agent 生命周期内的【同步钩子】
    → pre-step 裁剪 / 工具审批 / 日志——单线程语义（不加锁、有序）
  邮局（Mailbox）＝ 跨线程/跨 agent 的【异步通信】
    → 对话投递 / 控制指令 / 结果回传——线程安全队列

为什么分两条（关键判断）：
  · 事件是"本 agent 循环内的检查点"——同步（不跨线程，无需锁）
  · 邮局是"agent 之间/跨线程"——异步（队列天然线程安全）
  → 不为并发付费：事件不加锁，邮局用队列
  → 跨线程 emit 事件 = 竞态源（前车之鉴）——一律走邮局

控制面收口（职责分离）：
  steer（改方向）→ 走邮局（消息——下轮生效）
  stop（终止）→ 保持 Event 信号（立即生效——中断不是消息流）
```

### 第 4 步：可靠投递（NACK 退信——面试加分：想到失败场景）

```
未知 target 投递失败 → 不能静默丢弃（fail-closed）：
  → 回执 NACK 给发送方（邮件退信语义）
  → data 带 original_id / original_target / reason
  → 发送方 drain 邮箱能看到"哪条消息没送到 + 为什么"

防递归（细节）：NACK 不再生成 NACK——最多原始 + 1 回执
```

### 第 5 步：A2A 预留（面向未来——面试加分：有前瞻性）

```
Message 三要素（id/sender/target）＝ A2A 协议对齐
  → target 未来可拓 ip:port:agent_id（远程寻址）
  → ForeignMailbox 接口预留（本地投递队列 / 远程投递网络——换后端不换接口）
  → 架构哲学：先有统一抽象，未来接协议 = 加适配器（同 Gateway 传输层哲学）
```

## 五、踩坑复盘（面试加分——有血有肉的细节）

```
① 消费者互清空：drain_steer/drain_messages 共用 drain()（取空整个 inbox）
   → 先取 steer 连带清掉 message（数据丢失！）——真实 bug
   → 修复：drain_by_type（按类型隔离消费）
   面试点：消费方法必须按类型隔离——不能"全量取再过滤"

② 主 agent 只收不读：mailbox 建了但主循环不消费（只有子 agent 消费）
   → steer 主 agent 无效（消息堆积）——不对称缺陷
   → 修复：Agent 构造统一挂 pre-step 消费钩子（主/子一致）

③ 连续 user 注入：message + steer 同时存在 → 相邻两条 user
   → 可能触发 LLM 400（role 必须交替）——真实 API 兼容坑
   → 修复：合并成一条 user（| 分隔）
   面试点：多 agent 消息注入 LLM 上下文时，要防格式破坏

④ 同步/异步路径分叉（设计决策）：工具路径（delegate_task）不走邮局
   → message.log 无记录（可观测缺口）
   → 决策：两个应用场景（LLM 自动外包 vs 用户手动派活）各走各的
```

## 六、面试问答弹药（准备这些追问）

```
Q：为什么不用现成的消息队列（RabbitMQ/Kafka）？
A：单机 agent 场景——进程内队列足够（Kafka 是分布式方案，杀鸡用牛刀）；
  但设计对齐了它的模式（topic 汇聚 + 消费者分发）——未来分布式可平滑迁移

Q：中央队列会不会成为瓶颈？
A：单机几十 agent、控制指令低频——不会（瓶颈是 LLM 秒级，不是队列微秒级）；
  若高吞吐事件流，可换有界队列 + 背压（设计预留了）

Q：同步和异步怎么选？
A：通信模型统一（邮局），等待策略分开——工具调用必须同步（协议约束），
  后台任务异步（邮局回传）；同步/异步是执行策略，不是通信方式

Q：事件总线和邮局为什么不用一个？
A：语义不同——事件 = 本 agent 循环内同步钩子（插件横切），
  邮局 = 跨 agent 异步通信；混用会让事件总线承担线程安全问题（跨线程 emit）
```

## 七、一句话收尾（面试结尾用）

> "这个通信模型的本质是：**把'谁和谁通信'从 agent 代码里抽出来，变成可审计、可路由、可扩展的基础设施**——agent 只感知自己的邮箱，Dispatcher 管路由，未来 A2A 只是换一个后端适配器。"
